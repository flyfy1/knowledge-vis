## 1. Decisions as taken

| # | Decision |
| --- | --- |
| D1 | One Markdown file per language (`content.zh.md`, `content.en.md`); the build checks parity mechanically. |
| D2 | Build-time rendering; outputs (`index.html`, `copy.zh.js`, `copy.en.js`, `refs.json`) are committed, so deploy stays `git archive \| rsync`. |
| D3 | Authorship follows content through a `Derived-From: <old> -> <new>` commit trailer (AUTHORSHIP.md §4, §9 entry 2026-11-16). |
| D4 | A mechanical migration does not repoint `sourceRevision`; the label credits the content. |
| D5 | Essays first, then lessons. `variants/claude-code/` is frozen; LeetCode keeps its pipeline and only gets chrome and registry rows. |
| D6 | Static `/en/` twins later, once essays are migrated. |
| D7 | Positional keys (`chN.pK`) plus explicit `{#key}` where a key is referenced or out of sequence. Renumbering shows as drift. |
| D8 | `KNOWLEDGE_PAGES` becomes generated (Phase 2); categories, subtopics, FEATURED and ESSAYS order stay hand-edited. |
| D9 | Prose references never become atlas edges. Missing edges are listed as a to-do. |
| D10 | The runtime 《title》 linker skips template pages (`site-nav.js`, `html[data-template]`); for them it is a build lint that suggests `[[slug]]`. |

## 2. Commands

```sh
node scripts/build-pages.cjs <page-dir>...      # write index.html, copy.zh.js, copy.en.js, refs.json
node scripts/build-pages.cjs --all              # every live page with a page.json
node scripts/build-pages.cjs --all --check      # in memory; exit 1 on drift, parity, refs, bindings, partials
                                                # also reruns each page.json generator in a scratch copy (§3a)
node scripts/build-pages.cjs --print-bindings <dir>   # each {=name}: its value and the keys that use it (exit 1 on build errors)
node scripts/build-pages.cjs --print-budgets <dir>    # inline-SVG diagram labels: room, zh / en share (§7)
node scripts/convert-essay.cjs <page-dir>       # migration: write sources next to a live essay and prove equivalence
node tests/site-template.cjs                    # fixture build, failure modes, converter round trip, site-nav skip
```

- `--all` covers only registered live pages whose `page.json` has a `"layout"` (§3b). Untracked drafts and the
  fixture site are never included.
- An unregistered draft is built by naming its directory. Its page.json has no `"status"`, so the build reads
  slug, path, category, subtopic and stage from its `page.json` when that names `category` and `path`, else from its
  `REGISTRY.json` (and the title from there), and warns `draft: …`. The
  draft has no backlinks, related pages or provenance label, and no other page can `[[link]]` to it until it is
  registered. A `page.json` slug that differs from the slug registered for that directory is an error.
- `--no-chrome --no-prefill` rebuild the pre-template page byte for byte. They exist for equivalence checks;
  never commit their output.
- `--root <dir>` points every tool at another site root (the tests use `tests/fixtures/site-template/`).
- The Pages workflow runs `--all --check` before publishing and does not publish `templates/`.

## 3. Files of a migrated page

```
<category>/<subtopic>/<slug>/
  page.json         slug, kind, layout, scripts, version (the ?v= cache key), provenanceNote; optional prefill,
                    languages, dynamicKeys, generators, legacyLayout (§3a); once registered also category,
                    subtopic, stage, status, path, tags, order (§3b)
  content.zh.md     the Chinese text: front matter, chapters, directive blocks        (source, edit this)
  content.en.md     the same skeleton in English                                       (source, edit this)
  page.css          the page's own styles, inlined by the layout                       (source)
  figures/*.html    language-neutral partials: labs, diagrams, raw-HTML regions        (source, or generated:
                    a partial a page.json generator writes starts with <!-- GENERATED by <script> … -->)
  tools/*.cjs       optional: the page's own generators of partials (page.json generators)  (source)
  bindings.cjs      optional: prose numbers computed from models.js                   (source)
  models.js app.js  unchanged page code                                                (source)
  index.html copy.zh.js copy.en.js refs.json                                           (GENERATED, do not edit)
  REGISTRY.json BRIEF.md tests/                                                        (unchanged; §3b)
templates/layouts/essay.html   the essay layout (head, top bar, hero, TOC, sections, footer, scripts)
scripts/lib/template.cjs       registry, refs, inline Markdown, content parser, builder
```

### 3a. Optional page.json fields

| Field | Meaning |
| --- | --- |
| `"prefill": false` | no pre-fill (§8). |
| `"languages": {"en": "stub"}` | English is a structural stub while the translation is pending. The build warns, allows Chinese in `content.en.md`, and writes `data-lang-en="stub"` on `<html>`, so `app.js` can fall back to Chinese (§9a step 2). The default, `"native"`, makes Chinese text or `[EN pending]` in any English string a build error. |
| `"dynamicKeys": {"ch4.say": ["norm", "sub"]}` | keys a script builds at run time (`t('ch4.say.' + cls)`). Each `prefix.value` must be defined. Once a page declares any, every `t('x.' + …)` or ``t(`x.${…}`)`` prefix in its `scripts` must be declared too. |
| `"generators": [{"run": "tools/diagrams.cjs", "writes": ["figures/dg-*.html"]}]` | partials written by a script in the page directory. Each matching file must start with `<!-- GENERATED by tools/diagrams.cjs … -->` (the build strips that line when it inlines the partial). `--check` runs the generator in a scratch copy of the page directory and fails on any difference, so a hand edit to a generated partial is caught. A generator reads and writes only inside its page directory: `run` must be a relative `.cjs`/`.js` path with no `..` and `writes` globs under `figures/`, or the build fails and `--check` runs nothing (review 2026-11-16: a `run` of `../../…/x.cjs` reached the same absolute file from the page and from the scratch copy, and `--check` executed it). The rerun is not a sandbox: the generator is page code and must write through `__dirname`, as `tools/diagrams.cjs` does. |
| `"legacyLayout"` | whitespace of a converted hand-written page (§10). |

Every generated file says so in its first line (`<!-- GENERATED … -->`, `/* GENERATED … */`, refs.json
`"_generated"`). Category, subtopic, stage and status come from the registry fields of `page.json` (§3b); title and
desc from the content.

### 3b. The registry (Phase 2, 2026-11-16)

**One rule: a page is registered by a `page.json` with a `"status"`** (`"live"` or `"planned"`), in the page's own
directory. Everything else is generated from those files by `node scripts/build-registry.cjs` (`--check` in tests):

| Projection | What |
| --- | --- |
| `pages.config.js` `KNOWLEDGE_PAGES` | the block between `/* ===== GENERATED: KNOWLEDGE_PAGES …` and `/* ===== END GENERATED … */` (D8). The rest of the file (categories, stages, subtopics, FEATURED, ESSAYS order, the header) stays hand-edited. |
| `site-registry.json` | `pages` (place, kind, status, template flag, title, desc, `anchors`, owned `concepts`), `adapters.leetcode`, `concepts` (atlas nodes whose primary lesson is a registered page: page, anchor, title, merged aliases), `edges` (`ref`: every scanned link between live pages, `slug#chN` → `slug#anchor`; `seeAlso`: REGISTRY.json `relatedPages`), `backlinks` (what template pages render). One entry per line. |
| `CONCEPT-MAP.md` | the page → concept → anchor tables between `<!-- GENERATED:registry-concepts -->` markers, after the atlas appendix. Hand-written text elsewhere stays. |
| `specs/atlas-edge-todo.md` | D9: linked page pairs that no atlas edge covers (rule in its header). Never turned into edges. |

site-nav-data.js (build-site-nav.cjs) and the template build (build-pages.cjs) read the same registry through
`scripts/lib/template.cjs` `createSite`, which calls `scripts/lib/registry.cjs`.

**page.json kinds.**
- **Metadata-only** (no `"layout"`): a hand-written page. Fields: `slug`, `kind` (essay | lesson | demo | tool),
  `title` and `desc` `{zh, en}`, `tags`, optional `languages: ["zh"]`, `category`, `subtopic` (optional only for
  entrance pages such as `atlas/`), `stage`, `status`, `path`, `order`. The seed commit wrote one for all 227
  hand-written pages from their pages.config.js rows.
- **Template page** (`"layout"`): the fields of §3/§3a plus `category`, `subtopic`, `stage`, `status`, `path`, `tags`,
  `order`. No `title` / `desc` (an error): they are the `# … {#hero}` heading (plain text; markup there is an error)
  and the front-matter `desc` of each `content.<lang>.md`.

**Checks** (each names the page.json): `path` equals its directory, and is `<category>/<subtopic>/<slug>/` when a
subtopic is given; category and subtopic exist in the hand-edited tables; stage, status and kind are known values;
slugs and orders are unique; title, desc, tags are bilingual. Not scanned: `.git`, `node_modules`, `.claude`,
`.agent`, `.runs`, `tests/fixtures/`, `specs/`, `variants/`, `templates/`.

**Order.** The home page lists registered pages in block order (live first). It is page.json `"order"` (the seed
used 10 × the old position); a page without one goes after every ordered page, by path. So a new registration leaves
`order` out.

**Hand edits.** `--check` compares the block with what the page.json files give and says what happened: a row with
no page.json (pasted by hand: "write page.json, or run --adopt"), a field that differs from its page.json, a
page.json not yet in the block, or `KNOWLEDGE_PAGES` changed outside the fence. `--adopt` moves rows that have no
page.json into new ones (ordered last) and takes hand edits of existing rows into their page.json; on a template page
a title or desc that differs from the content is refused. The same command, on the unfenced file, made the seed commit.
- A plain run (no flag) refuses while the block holds a row that no page.json registers, and writes nothing: it used to
  drop such a row with only "wrote pages.config.js", and the `--check` hint pointed at the plain run (review
  2026-11-16). `--check` now says `--adopt` for that case. To unregister a page on purpose, delete its row from the block
  too. A hand edit of an existing row is still overwritten by a plain run (page.json is the source; `--check` names it).
- `--adopt` checks every row before it writes any page.json, and leaves a page.json alone when only its key order
  differs. An adopted row gets `max order + 10`, so it sorts before pages registered without `order` (by design: the
  seed order is kept; give it no special meaning).
- `build-pages.cjs <dir>` on a metadata-only page.json says so ("no layout … hand-written page") instead of failing on
  a missing `content.zh.md`.

**Two registrations at once (merge).** Each branch's run rewrites the same generated files, so a merge conflicts in
`pages.config.js`, `site-registry.json`, `site-nav-data.js` and `specs/atlas-edge-todo.md` (and `CONCEPT-MAP.md`,
`atlas/`, `search/` when both imported concepts). Resolve the hand-edited part of `pages.config.js` (KNOWLEDGE_ESSAYS,
subtopics) by hand, take either side of every generated block and file, then rerun `build-registry.cjs`,
`build-site-nav.cjs`, `build-pages.cjs --all` (and the atlas and search builds if concepts were imported) and commit.
Order needs no resolving: pages without `order` sort by path. A conflicted `pages.config.js` fails to parse, so the
scripts cannot run before the conflict markers are gone (simulated in the review: two drafts on two branches merge to
the same bytes as registering both on one branch).

### 3c. Lessons (Phase 3, 2026-11-16)

A lesson is a page whose strings live in an `i18n.js` table (`const STR = { zh: {…}, en: {…} }`) and whose body is
steps (`<section id="stepN">`) behind a step nav. `page.json` `"layout": "lesson"` makes it a template page; the same
`build-pages.cjs` builds it and `convert-essay.cjs` converts it (it recognises a lesson by an `i18n.js` and no
`copy.zh.js`, so conversion commits keep the one `Built-By` line of §10).

```
<category>/<subtopic>/<slug>/
  page.json        registry fields (title and desc stay here: a lesson's card title is not its <h1>), layout "lesson",
                   version (the ?v= of i18n.js), titleKey (the key <title> shows), enCjk, legacyLayout;
                   optional runtimeKeys, placeholderRepeats (below)                                     (source)
  content.zh.md    page-wide strings, then one "## <h2 text> {#stepN h2=<key>}" per step                   (source)
  content.en.md    the same skeleton in English                                                         (source)
  layout.html      a converted page's own frame: its head, header, nav, footer and scripts with {{slots}}  (source)
  figures/*.html   step markup that is not a plain keyed paragraph (stages, controls, cards)            (source)
  i18n.shell.js    the page's i18n runtime with /*@i18n-table@*/ where the table goes                   (source)
  style.css app.js unchanged page code                                                                  (source)
  index.html i18n.js refs.json                                                                          (GENERATED)
templates/layouts/lesson.html  the shared frame for a lesson written natively (no layout.html)
scripts/lib/lesson.cjs         compileLesson, buildLesson, convertLesson, splitI18n
```

**Content.** Keys are the table's own keys, flat and absolute (`s0e`, `nav0`, `docTitle`): app.js and the page tests
name them, so they survive unchanged. No positional keys.

```markdown
---
lang: zh
---

::: strings                                  ← page-wide keys (header, footer, <title>, app-only keys before step 0)
docTitle: 二维线性变换 · 一步一交互
:::

## 四个数，拖动整个平面 {#step0 h2=s0t}        ← <section id="step0">, its <h2 data-i18n="s0t">

::: strings
nav0: 0 网格变形                              ← the step-nav item of this step (nav=<key> when it is not nav<N>)
:::

第 0 步 · 钩子 {#s0k .step-kicker i18n=text}   ← <p class="step-kicker" data-i18n="s0k"> (rendered above the h2)

矩阵 **A** 不需要逐点…… {#s0e .explain}        ← <p class="explain" data-i18n-html="s0e">

::: html step0-1                             ← figures/step0-1.html and the keys it names
pIdentity: 单位矩阵
:::

::: strings                                  ← keys only app.js uses, with the step they belong to
s0say: 已运行 {n} 次
:::
```

- Heading attributes: `h2=<key>`; `h2id=<id>` (an `id` on the h2); `i18n=html` (`data-i18n-html`); `.class`;
  `nav=<key>`; `pre=N` (N blocks above the h2; the default is the leading `.step-kicker` paragraphs); `h2part=1` (the
  h2 is written in one of the step's partials, because its hand-written text was not its zh string, or because it sits
  inside a wrapper such as `<div class="finale">` that holds the whole step (15 lessons of batch B); the heading still
  defines the key).
- Paragraph attributes: `{#key}` always; `.class`; `tag=div|h3|h4`; `i18n=text` for `data-i18n` (default
  `data-i18n-html`). Inline Markdown and `[[refs]]` as in §4–5; the converter writes them only where they render back
  to the exact string.
- Anything else in a step (and every `<h2>` / paragraph whose value has a line break or edge spaces) is `::: html`.
  Lists, `:::` lab/diagram/footer, `###` and `---` are errors in a lesson.

**Frame.** `layout.html` (or `templates/layouts/lesson.html`) holds the page outside the steps. Slots: `{{generated}}`
and `{{htmlAttrs}}` (chrome), `{{title}}` (zh value of `titleKey`), `{{v}}` (`?v=<version>` on `i18n.js`), `{{up}}`,
`{{siteNavCss}}` / `{{siteNavJs}}` (from `build-site-nav.cjs`), `{{crumbs}}` (the static breadcrumb, where site-nav.js
mounted it: before the `<h1>`, or before an eyebrow/kicker line above it), `{{provenance}}`, `{{badges}}` (shared layout
only: the edition-compare link when `variants/claude-code/<slug>/` exists), `{{stepNav}}` (one item per step),
`{{steps}}` and `{{linkedFrom}}` (after `</main>`; its box is a `.step-inner`, centred like a step by
`section.site-xref` in `lesson-shell.css`, because the pages centre steps through their own `.step` rule). An unknown slot fails; a slot with
content to render but missing from the frame fails.

**legacyLayout** (converted pages; safe to delete, then the page shows drift until rebuilt):
- `section` (the step's open and close markup, `{id}` / `{n}` patterns or one string per step), `indent` and `leads`
  (whitespace before blocks), `mainGaps` (text between steps, including the hand-written `<!-- 步骤 N -->` comments),
  `stepNav` (`{item, end}` pattern, or `false` when the hand-written nav stays literal in `layout.html`);
- `filled`: the elements the hand-written page had pre-filled (`key`, `key#2`, `aria:key`). A build with
  `--no-prefill` fills exactly these, so the round trip is byte for byte; the normal build pre-fills every empty element
  (§8) anyway;
- `label`: the hand-written shape of the provenance label with `{{developer}}`, `{{edition}}`, `{{sourceRevision}}`,
  `{{short}}`, `{{scope.zh}}`, `{{scope.en}}`, `{{kind.zh}}`, `{{kind.en}}`; the values come from `page-provenance.json`,
  so a repoint is an edit there plus a rebuild. Without `label` the standard label (§8) renders.

**i18n.js.** Generated: a GENERATED comment, then `i18n.shell.js` with the table in place of the marker, written as
`{ zh: { key: "value", … }, en: {…} }` (identifier keys bare, so tests that look for `s0t:` or slice to `\n};` keep
working). The output name stays `i18n.js`, so `app.js`, `index.html` script tags and page tests are untouched. The
chrome's `site.*` strings are appended to both tables. `page.json` `version` is the `?v=` of the i18n.js script tag;
bump it whenever the generated file changes (§9 step 4).

**Checks** (as §7, adapted): parity of skeleton, key set, `{v}` placeholders and link targets; every key a partial or
the frame names exists; an English string with Chinese fails unless `page.json` `enCjk` lists its key (the converter
records the keys that already do, such as a footer `二维线性变换 Linear Maps`); the D10 lint; raw-link warnings. No
registry-text check (the title stays in page.json). Warnings: `stale:` names keyed elements in `figures/` whose
hand-written text is not their zh string (the runtime replaces it; readers without JS see it).

**Batch B shapes (2026-11-16).** Each is recorded by the converter, so a conversion commit needs no hand edit:

  regardless, as for every lesson.
- `page.json` `runtimeKeys: ["stepWord", …]`: keys the markup names that a second `{zh, en}` table in `i18n.shell.js`

  first `.step`) onto the block on load and resize (lessons without lesson-shell.css only; without JavaScript the
  4px stays). Measured on all 111 pages with a block at 1280/390/320: 0 off (was 0/45/45).
- `page.json` `placeholderRepeats: ["s5roImp"]`: keys whose zh and en strings use the same placeholders a different
  number of times (fractions zh 「读作 {q} 又 {d} 分之 {r}」 has no English counterpart). Parity then compares the set of
  placeholders instead of the multiset; a different set still fails (chicken-rabbit, fractions, polygon-angles).

**Pre-fill and aria.** Every empty keyed element is pre-filled as for essays. `aria-label` is pre-filled only when the
page's runtime (`i18n.shell.js` or `app.js`) translates `data-i18n-aria`; most lesson runtimes do not, and a Chinese
`aria-label` would then stay Chinese in English. The static breadcrumb's `aria-label` is therefore missing from those
pages' HTML. On the hand-written pages site-nav.js named the breadcrumb it mounted, but it skips `html[data-template]`,
so the converted lessons first shipped with an unnamed breadcrumb landmark (14 of 17; the Phase 3a review). Since
then site-nav.js, on a template page whose `nav.site-nav` has no `aria-label`, sets 页面位置 / Breadcrumb from
`<html lang>` and follows it on a language switch (tests/site-nav-browser.cjs, convolution zh and en). A pre-filled
label (runtime translates `data-i18n-aria`) is left alone.

**Backlinks.** A link in a lesson is credited to its step: the linked-from row on the target reads
`《课名》：该课第 N 步 → 本页第 M 章` / `Title: its step N → this page chapter M`, and a lesson's own linked-from block
names steps (`本页第 N 步` / `this page step N`). A link inside a step's `::: html` partial (`figures/<name>.html`) is
credited to the step that names the partial, like a keyed paragraph (`scanLinks`, template.cjs). Until the Phase 3a
review it was not: about 37 links in the 17 converted lessons' partials (mostly the step-6 "where next" cards) gave
source-less rows (`《课名》：→ 本页第 N 步`), next to a credited row for the same target in kalman ↔ eigenvectors.

**Page-wide keys.** The layout names these keys, so every page defines them, or the build fails:
- front matter `title` and `desc`;
- in the first `::: strings` block (before `# … {#hero}`): `nav.back`, `nav.lang`, `toc.label` and `toc.title`;
- in the hero's `::: strings`: `kicker`;
- one `::: footer`.

**Keys.**
- A paragraph without a class gets the next positional key, `<chapter>.p1`, `p2`… The counter runs through the
  whole chapter, labs included.
- `.law` maps to `<chapter>.law`, `.take` to `<chapter>.limit`, and a hero paragraph to `hero.<first class>`.
- Anything else needs `{#key}`. Keys written inside a chapter are relative (`f.seagate` → `ch9.f.seagate`). A key
  whose first segment is a section id is absolute.
- `keys=<prefix>` on a block makes its entries relative to that prefix instead.
- Trailing attributes: `{#key .class tag=div style="…"}`. A line holding only `{.class …}` applies to the next
  list or paragraph.

**Inline.** `**bold**`, `*em*`, `[[ref]]`, `{=name}`, `{v}` (runtime, untouched), and raw inline HTML for
the rest (`<br>`, `<span class="tag m">`, external `<a href>`). Escapes `\*`, `\[`, `\{`, `\\` give the
literal character. A paragraph that would read as block syntax (`- `, `1. `, `#`, `:::`, `{#`, `<!--`) starts
with a backslash, which is dropped.

**Directives.** Each `::: <type> <name> [keys=<prefix>]` block holds `key: value` lines (a value that starts
or ends with a space, contains a line break or starts with `"` is written as a JSON string).
- `strings`: labels, units, aria text, live sentences. `toc:` and the hero's `kicker:` are special.
- `lab`: an interactive figure. Its DOM is `figures/<name>.html`, owned with `app.js` because `app.js` binds
  to its ids. It renders inside `<div class="wide">`.
- `diagram`: a static schematic (STANDARD.md §4a). Its markup is `figures/<name>.html`, inside the prose
  column. It comes in two shapes, both with all labels in the block:
  - **(a)** the shell `app.js` fills (`<figure class="dia" data-dg="x"><div class="svg"></div><figcaption …>`),
    with every label `app.js` reads (`dg.x.*`) listed in the block even when the partial does not name it;
  - **(b)** an inline `<svg viewBox …>` whose `<text>` elements carry `data-i18n` keys.

  Numbers drawn on a diagram use `{=name}` like prose, or come from `models.js` in `app.js`.
  - `place=wide` (`::: diagram dg-d1 keys=d1 place=wide`) puts the diagram in its own `<div class="wide">` between
    prose columns, as a lab is (how-pcie-works).
- `html`: any other raw region inside the prose column (a table, a hand-built grid). Keys it names go in the
  block. The converter uses it wherever a region is not prose, a list, a lab or a diagram.
- `footer`: Markdown paragraphs, all under the one key `footer`. `::: footer wrap=none` is one paragraph without
  `<p>` (older pages). When every paragraph ends in `{#key}`, each is its own key `footer.<key>` and renders as
  `<p data-i18n-html="footer.<key>">` in the footer column (how-sas-works: `{#sources}`, `{#models}`, `{#ai}`).

**Prose columns.** A chapter's prose sits in `<div class="wrap">`; a lab or a `place=wide` diagram ends it, and the
prose after starts a new one. A line holding only `---` inside a chapter ends the column without a lab, so two
columns follow each other (how-sas-works ch7). A paragraph that is literally `---` starts with a backslash.

A partial is language-neutral. It holds no text, only `data-i18n` / `data-i18n-html` / `data-i18n-aria`
keys, and the build fails if it names a key no block defines.

## 5. Cross-references

| Syntax | Resolves to | Text |
| --- | --- | --- |
| `[[slug]]` | `../slug/`, relative to this page | the target's title in this language |
| `[[slug#ch7]]` | `../slug/#ch7` | target title |
| `[[slug#ch7\|text]]` | same | as written |
| `[[#ch3\|text]]` | `#ch3` on this page | as written |
| `[[concept:id-or-alias]]` | the concept's primary page and anchor in the atlas | the concept title |

- The build fails on an unknown slug, an anchor the target does not have, an unknown or ambiguous concept (an
  alias owned by two concepts is an error, never a guess), and a zh and en ref that point to different targets.
- Prefer `[[…]]` to a hand-written `<a href="../…">`. Raw links still work. The build warns when one points
  at no live page or a missing anchor, and compares targets between languages, in either quote style.
- The lint (D10) warns about a mention of another live page's title that is not a link. It matches what the
  runtime linker (`site-nav.js`) links on hand-written pages: zh 《title》, en “Title” with an optional `,` or `.`
  inside the closing quote and `'` / `’` interchangeable, and `<cite>Title</cite>`. It never rewrites prose; decide,
  then write `[[slug]]` or leave the quotation. When a hand-written page is converted, every lint line is a link
  readers have today; the Phase 1 batch A review found the first version missed `“Title.”` (2026-11-16).
- Concepts resolve through the table search uses (Phase 2): `atlas/data.js` node ids, titles and aliases (the aliases
  already merged from the node, `atlas/graph/aliases.json` and the essay fragments), each compared after
  `search/concept-search.js` `squash` (NFKC, lower case; spaces, hyphens, middle dots, apostrophes ignored), so
  `[[concept:Cache-Line]]` finds "cache line". It stays an exact match: search's prefix and contains scoring is not
  used, so `[[concept:写放大]]` does not resolve (the NVMe concepts are titled「写放大、垃圾回收与 Trim」and aliased
  「写放大 WAF」). A term two concepts own is an error naming both (40 such terms in atlas/data.js on 2026-11-16).

## 7. The checks (`--check` and every build)

- **Drift:** each output equals a fresh build.
- **Parity:** the same block skeleton in zh and en (blocks, keys, figures), the same key set, the same `{v}`
  multiset per key, the same `{=…}` per key, and the same link targets per key.
- **Refs:** as in §5.
- **Bindings:** every name known, every binding used.
- **Partials:** each exists and names only defined keys.
- **Layout keys:** every `data-i18n*` key in the built page, including those the layout and chrome name, is
  defined (§4 「Page-wide keys」).
- **Languages:** unless `page.json` says `"languages": {"en": "stub"}`, no English string holds Chinese text (also inside
  an attribute, `<abbr title="目录">`) or `[EN pending]` in any case (§3a). A stub on a registered page is an error,
  on a draft a warning (follow-up review 2026-11-16 §5).
- **Registry text:** `REGISTRY.json` `title.<lang>` equals the `# … {#hero}` heading and `desc.<lang>` equals the
  front-matter `desc`; a registered page's `pages.config.js` title equals the heading too. Edit them together
  (they merge in Phase 2). The SIMD review found an English desc an order of magnitude off the registry's.
- **Dynamic keys:** as declared in `page.json` `dynamicKeys` (§3a).
- **Generated partials:** headers as declared in `page.json` `generators`; under `--check` the generator's fresh
  output equals the committed partials (§3a).
- **Label room** (inline-SVG diagrams, shape (b)): for every `<text>` with `x`, `y` and `font-size` attributes in a
  partial's `<svg viewBox>` (none inside a `transform`), the build estimates the width of its string in each
  language. It fails when the string is wider than the viewBox leaves for its `text-anchor`, or when two labels on
  the same baseline overlap. The estimate uses rough per-character widths (CJK 1 em, Latin lower case about
  0.52 em, capitals 0.64, monospace 0.6). `--print-budgets <dir>` lists each label's room, its zh and en share,
  and about how many Latin or CJK characters fit.
  - Calibration (2026-11-16, how-a-cpu-does-math): every shipped label is at most 85% of its room and none
    overlap. Of the seven English labels its review had to shorten, the check catches the five that left their
    room or hit a neighbour (`positive`, `remaining bits OR-ed together`, `fused multiply-add: one rounding`,
    `rounded product (24 bits)`, `separate: two roundings`).
  - It misses the two that crossed a line (`wait for previous result` on its arrow, `spacing 1/8` under a leader
    line). Text over a line, labels drawn on a canvas and overflow inside controls still need the browser test and
    a screenshot.
- **Warnings (do not fail):** lint suggestions and raw links to missing pages or anchors.

Backlinks are generated. When a page gains a link to a migrated page, the migrated page's `index.html` and
`refs.json` drift, and `--all --check` fails until someone runs `node scripts/build-pages.cjs --all`. Run it
after registering a page or adding cross-links.

A backlink is a link written in another page's sources. For an unmigrated page those are `copy.zh.js`,
`i18n.js` and `index.html`. For a migrated page they are `content.zh.md` (compiled, so it has no `site.*` keys),
plus `figures/*.html`. Its `index.html` is not scanned, because pre-fill copies the copy table into it, and the
`site.*` keys are themselves generated backlinks. Scanning either would make links echo between migrated pages,
and one `--all` pass would no longer be final (review 2026-11-16). The generated `copy.zh.js` is not scanned
either: `--all` builds pages in order, so a page built early would read a later page's copy table from before
this pass and miss a link just added to its Markdown (Phase 1 batch A review, 2026-11-16). A link in a key outside `chN.*` (a diagram caption `dg.x.cap`, a lab
string) is credited to the chapter the block sits in; before, it showed as a bare `→ 本页第 N 章` with no source
chapter (how-a-nic-moves-packets ← storage-over-a-network ch6).

## 8. Chrome (what the layout adds)

- `<html data-template="essay">` and a GENERATED comment.
- A static breadcrumb with the site-nav markup and styles (`nav.site-nav`, `site-nav.css`).
- A "被这些页面引用 / Linked from" block (backlinks with source and target chapters) and "相关页面" (REGISTRY
  `relatedPages` minus backlinks), styled by `.site-xref` in `site-nav.css`. A row reads
  `《来源》：该文第 3 章 → 本页第 2 章` / `Source: its chapter 3 → this page chapter 2`: the first chapter is the
  linking page's, the second this page's.
- Their strings are `site.*` keys added to the page's own copy tables, so the page's i18n swaps them and the
  English CJK sweep needs no exemption. Content may not define `site.*` keys; the build fails on one, because
  page tests skip `site.*` in their link and number scans.
- The site-nav include lines come from `scripts/build-site-nav.cjs` (`includeLines`), so its `sn-` cache key
  has one source. `build-site-nav.cjs` never writes into a template page. It reports a stale one with the
  build-pages command. `site-nav.js` does nothing on `html[data-template]`.
- The provenance label is rendered from `page-provenance.json` plus `page.json.provenanceNote` (the free-text
  first paragraph). To repoint a label, edit `page-provenance.json` and rebuild. The AGENTS.md rule about
  `data-source-revision` / link / short SHA is then satisfied by the build.
- **Pre-fill:** the zh text inside every empty `data-i18n*` element and `aria-label` from `data-i18n-aria`, so
  readers without JS see the essay. Values with `{v}` placeholders are left to `app.js`. `"prefill": false` in
  `page.json` turns it off. `scripts/lib/prefill.cjs` holds `prefill` and its exact inverse `unprefill`, which page
  tests use to read the markup without it (§10 step 3).

## 9. How agents edit a migrated page

1. Edit `content.zh.md` and `content.en.md` together, keeping the skeleton identical. Edit `figures/*.html`,
   `page.css`, `page.json`, `bindings.cjs`, `models.js` or `app.js` as needed.
2. Run `node scripts/build-pages.cjs <page-dir>`, then the page's own tests and `--all --check`.
3. **Never hand-edit `index.html`, `copy.zh.js`, `copy.en.js` or `refs.json`.** The next build overwrites them,
   and `--check` fails until then.
4. Cache keys: when a script file changes, set `page.json.version` (same rule as specs/essays.md step 7) and
   rebuild.
5. Commit sources and outputs together with normal trailers. `page-provenance.json` `sourceRevision` follows
   AGENTS.md as before; the label in the page updates on rebuild.
6. Haiku translation: give it the whole `content.zh.md` and the contract below; it returns `content.en.md`.
   Then build. Parity failures name the key.

**Translation contract.** Translate the text only. Copy verbatim:
- everything inside `{…}`;
- the target part of `[[target|text]]` (translate only `text`; a bare `[[target]]` stays as is);
- every `::: …` line, every `key:` prefix and every `{#key .class}`;
- the front-matter keys.

Do not merge or split paragraphs or list items. Keep each diagram label within the room
`node scripts/build-pages.cjs --print-budgets <dir>` lists (the build fails above 100%; aim lower, the estimate is
rough), and give the translator that listing with the Markdown.

## 9a. Writing a new essay directly in Markdown

Native template essays (the first: how-a-cpu-does-math, 2026-11-16) start here. Everything in specs/essays.md and
STANDARD.md still applies; only the files differ. Its BRIEF.md lists the friction the first one met; the items
below marked *(2026-11-16)* are template features added for them, so the next essay does not need page code.

1. **Files.** Create these in the essay's directory:
   - `REGISTRY.json` (essays.md「Files」), which the draft build reads. Its `title` must equal the
     `# … {#hero}` heading and its `desc` the front-matter `desc`, in both languages (the build checks, §7);
   - `page.json`: `{"slug", "kind": "essay", "layout": "essay", "scripts": ["models.js", "copy.zh.js",
     "copy.en.js", "app.js"], "version": "<date>"}`, plus the optional fields of §3a;
   - `content.zh.md` (§4, including the page-wide keys);
   - `page.css`, `figures/`, `models.js`, `app.js` and `tests/`.
2. **Runtime.** The template ships no i18n runtime. `app.js` must apply the copy itself:
   - `document.title` and the `data-i18n` / `data-i18n-html` / `data-i18n-aria` fill, with `{v}` placeholders;
   - the `#langToggle` buttons and the stored language;
   - **English pending** *(2026-11-16)*: until `content.en.md` is translated, write it as a structural stub
     (same skeleton, `[EN pending]` text) and set `"languages": {"en": "stub"}` in `page.json`. The build then
     allows it and writes `data-lang-en="stub"` on `<html>`; `app.js` treats English as absent while that attribute
     is there (`const enStub = document.documentElement.dataset.langEn === 'stub'`). Remove the field when the
     translation lands: from then on Chinese or `[EN pending]` left in English fails the build. Do not invent a
     page-wide `meta.en` string for this (how-a-cpu-does-math did before the field existed).

   Copy that head from `computing/systems/how-a-cpu-does-math/app.js` (the first 50 lines).
3. **Styles.** No shared theme exists yet. Start `page.css` from a recent essay's `<style>` block and keep only
   the classes the page uses. The layout's classes (`topbar`, `hero`, `kicker`, `toc`, `ch`, `num`, `wrap`,
   `wide`, `law`, `take`, `lab`, `dia`) must be styled. Set `overflow-wrap: anywhere` on prose that can hold very
   long numbers (a 55-digit exact value overflowed at 390 px).
4. **Diagrams.** Shape (b), an inline `<svg>` in `figures/<name>.html` with `data-i18n` labels, needs no `app.js`
   code. Shape (a) needs drawing code in `app.js`. A diagram that should span the wide column is
   `::: diagram … place=wide`.
   - **Label room** *(2026-11-16)*: give every SVG `<text>` explicit `x`, `y` and `font-size` attributes and no
     `transform`, so the build can check it (§7). Run `node scripts/build-pages.cjs --print-budgets <dir>` and hand
     the listing to the translator with the Markdown. Narrow variants (360 units) leave about 40 Latin characters
     for a centred full-width label.
   - **Generated partials** *(2026-11-16)*: when a script draws the diagrams or a table (how-a-cpu-does-math
     `tools/diagrams.cjs`), declare it in `page.json` `generators` and make it write
     `<!-- GENERATED by tools/<name>.cjs … -->` as the first line of every file. `--check` reruns it and fails
     on a hand edit. Workflow: edit the generator, run it, then `build-pages`.
   - Literal text in a partial must be language-neutral (digits, symbols, format names such as FP32); the build
     does not judge this, the page test should whitelist it.
5. **Keys.**
   - Two labs in one chapter each define `model.title`; give the second `keys=chN.x` (the build reports a
     duplicate key otherwise).
   - Only `.law` and `.take` paragraphs get implicit keys. Any other class (`{.sum}`) needs `{#key}`.
   - **Keys only a script uses** *(2026-11-16)*: list them in `page.json` `dynamicKeys`
     (`{"ch4.say": ["norm", "sub", "zero"]}`). The build checks each exists, and that every `t('x.' + …)` prefix
     in the scripts is declared.
   - A table of numbers is either one key per cell or a generated partial (above).
6. **Build and test.** Run `node scripts/build-pages.cjs <dir>`; the `draft:` warning is expected until
   registration. Write `content.en.md` (§9 translation contract) and rebuild until parity passes. Then run the
   page tests, the canvas sweep and the independent review on the built output.
   - `node scripts/build-pages.cjs --print-bindings <dir>` *(2026-11-16)* lists every `{=name}` with its value and
     the keys that use it, so a reviewer of the Markdown can read the numbers.
   - Pre-fill puts Chinese into `index.html`. A test that inspects the markup reads it through
     `unprefill(html, Z)` from `scripts/lib/prefill.cjs` (§10 step 3), or the page sets `"prefill": false`.
   - The build does not see overflow inside a control (a squeezed range label spilling onto the next control).
     Keep a browser check that each control's children stay inside it (how-a-cpu-does-math `tests/browser.cjs`).
   - `[[slug]]` resolves only to live pages; name an unregistered sibling draft in plain text and link it when it
     is registered.
7. **Commit.** Commit sources and outputs together, never the outputs alone.
8. **Registration.** Follow essays.md「Registering」:
   - add the registry fields to `page.json` (`category`, `subtopic`, `stage`, `"status": "live"`, `path`, `tags`; §3b),
     remove `"languages": {"en": "stub"}` (an error on a registered page) and run `node scripts/build-registry.cjs`;
   - add the `page-provenance.json` entry and rebuild the page (the label is rendered from it);
   - run `node scripts/build-pages.cjs --all`, which picks the page up and refreshes backlinks;
   - run `node scripts/build-site-nav.cjs` (it does not edit template pages) and `--all --check`.

## 10. Converting a page (Phase 1 procedure)

Only convert a page no one else holds. Drafts written in the old pattern are converted after they are
registered.

1. `node scripts/convert-essay.cjs <page-dir>` writes the sources. Then it rebuilds without chrome and pre-fill
   and requires `index.html` to be byte-identical and both copy tables key-for-key equal. If they are not, it
   exits 1 naming the first difference, and the sources stay for inspection. The old `index.html` and copy
   files are not touched.
   - The copy tables have the same keys and values, but key order may differ, so `copy.*.js` are not
     byte-identical.
   - The page's `page.json` is its registry row (§3b). The converter merges the template fields into it (keeping the
     registry fields, dropping title and desc, which the content now holds). A failed run puts the original
     `page.json` back (the attempted one is `page.json.converted`) and leaves `content.*.md`, `page.css` and
     `figures/`; delete those before you retry or commit anything else.
   - A page with more than one `<style>` block is refused. Merge them in `index.html` in a commit of its own,
     then convert. how-a-gpu-computes had two; they were merged in bb10f897.
2. Run the page's `tests/models.cjs` and `tests/browser.cjs` on a `--no-chrome --no-prefill` build. Its
   `index.html` is identical to the old page, and its copy tables are equal key for key.
3. **Decide on pre-fill before the full build.** Most 2026-11-15 computing essays have a `tests/models.cjs` check
   that forbids CJK in `index.html`, and some match regexes that expect empty elements (`<figcaption …></figcaption>`),
   so they fail on pre-filled text. Resolve it per page, either way:
   - in a separate authored commit, read `index.html` in the test through `unprefill(html, Z)` from
     `scripts/lib/prefill.cjs`. It is the exact inverse of pre-fill (same file, so they cannot drift): it removes a
     value only where it sits in the element whose key it is, and an `aria-label` only where it equals that key's
     value. A hand-typed string, or extra text next to a value, survives and still fails the check
     (tests/site-template.cjs pins this). On a page that is not yet converted it is a no-op. Checks that count links
     or literal numbers over the copy table skip the generated `site.*` keys. This is what batch A did;
   - or set `"prefill": false` in `page.json`.

   Do not loosen any other assertion.

**`legacyLayout` in page.json** records whitespace of the hand-written HTML so step 1 can compare byte for byte:
- `join`: blocks written on the same line as the previous one;
- `compactLists`: lists on one line;
- `gaps`: blank lines between head, sections, main and footer (`afterProvenanceCss`: a blank line before the
  site-nav stylesheet, how-sas-works and how-pcie-works);
- `compactSections`: every section written on one line, no whitespace inside it (how-pcie-works);
- `compactToc`: the table of contents on one line.

It is safe to delete. Only whitespace between block elements changes, and then the page shows drift until it
is rebuilt.

**What the converter handles.**
- **Heroes:** kicker, title, paragraphs, label.
- **Chapters:** a `.wrap` with `.num` and `h2`, then prose, labs and diagrams. Prose is `<p>` or `<div>` with
  `data-i18n-html`, plus `class` and `style`.
- **Lists and headings:** `h3` with `data-i18n`, and `ul` / `ol` with keyed `li`.
- **Diagrams:** `figure.dia`, either shape. A `figure.dia` or `figure.diag` alone in a `<div class="wide">`
  becomes `::: diagram … place=wide` (how-pcie-works).
- **Two prose columns in a row** become `---` between them (how-sas-works ch7).
- **A footer of keyed paragraphs** (`<p data-i18n-html="footer.sources">…`) becomes a `::: footer` whose
  paragraphs end in `{#sources}` (how-sas-works).
- **Everything else** becomes `::: html`.
- **Links:** double-quoted site links become `[[refs]]` when the round trip is exact. Single-quoted ones stay HTML
  (converting them would change the copy value).

Older essays with other hero or section shapes need converter variants. Where a region cannot be reproduced
exactly, keep it as `::: html`.
