## Computational correctness and causal mapping

The canonical first loop processes i=1..n−1, so its dependency left[i−1] is already final. A strict increase extends that neighbor's lower bound; otherwise left[i] remains 1, including equality. The second loop processes n−2..0 and similarly consumes final right[i+1]. The no-neighbor endpoint in each direction already has its exact bound 1. The merge occurs only after both scans; it is not an in-place relaxation of C. Termination is finite fixed ranges, and the final integer total matches the original callable semantics.

The cold transition R[1]:1→2 for [3,2,1] maps exactly to `ratings[1] > ratings[2]` and `right[1] = right[2] + 1`. Actual canonical Python execution was instrumented with `sys.settrace`, without replacing the algorithm: runtime locals contain right=[1,2,1], then [3,2,1], and finally candies=[3,2,1]. Undo in the UI returns to the saved post-operation snapshot; it does not run Python backward. In the simulation, arrays are sliced for every frame, preventing later writes from corrupting earlier history.

The proof's subtle step is sound: for a rising edge, R[i−1]=1, so max cannot unexpectedly raise the lower-rated previous child above the current child. Falling is symmetric, equality imposes no comparison. All allocations dominate L and R separately, and this feasible max dominates neither unnecessarily; thus it is componentwise minimal. The worked examples and proof expose the missing step beyond a mere claim that max “handles both sides.”
