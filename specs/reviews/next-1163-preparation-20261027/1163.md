# #1163 Last Substring in Lexicographical Order

Official source: https://leetcode.com/problems/last-substring-in-lexicographical-order/
The retained public response is HTTP 200, Hard, free, with statement and templates.
Python3: `Solution.lastSubstring(self, s: str) -> str`.
TypeScript: `lastSubstring(s: string): string`.
Input length is 1..400,000; characters are lowercase English letters. Return the
lexicographically greatest contiguous substring, not its index, a subsequence,
a sorted rearrangement, or simply the substring starting furthest to the right.

## Lexicographic semantics and suffix reduction

Compare strings at their first differing character. If neither differs before
one ends, the shorter proper prefix is smaller. Length is not a primary sort
key: `z` exceeds `az`, despite being shorter; `aaaa` exceeds `aaa` because the
latter is its proper prefix. Lowercase English inputs avoid locale/Unicode-order
ambiguities here.

Every substring `s[i:j]` with j < n is a proper prefix of `s[i:n]`, so extending
it to that suffix strictly increases it in lexicographic order. Hence no
non-suffix occurrence can attain the maximum, and the maximum among all
substrings equals the maximum among suffixes. This argument proves the reduction;
tiny exhaustive agreement alone would not. It does not make enumeration of all
suffix strings efficient for the full input limit.

The independent oracle enumerates every nonempty substring using both start and
end positions; it does not assume the suffix reduction when choosing its answer.
All 12 hand-worked results are checked against this oracle.

## A precise local elimination lemma, without a jump implementation

Let suffix starts i < j have k equal leading characters:
`s[i+r] == s[j+r]` for 0 <= r < k. Suppose both mismatch positions are in range
and `s[i+k] < s[j+k]`. For each t in 0..k, suffix i+t shares k-t leading characters
with suffix j+t and then has the same strictly smaller mismatch character.
Therefore i+t cannot be globally greatest, because the concrete suffix j+t
beats it. With the opposite mismatch, the same argument eliminates j+t using
i+t. Both compared starts are in range, since their mismatch indices are.
This argument remains valid when the ranges overlap; it uses equality at exact
positions, not an assumption that the compared regions are disjoint.

Reproduced traces in `example-checks.json` include:

- `aaaaab`, i=0, j=1: equal pairs (0,1), (1,2), (2,3), (3,4); mismatch (4,5),
  a < b. Starts 0..4 are each beaten by starts 1..5 respectively.
- `ababac`, i=0, j=2: equal pairs (0,2), (1,3), (2,4); mismatch (3,5), b < c.
  Starts 0..3 are beaten by starts 2..5 respectively.
- `zzazzz`, i=0, j=3: equal pairs (0,3), (1,4); mismatch (2,5), a < z.
  Starts 0..2 are beaten by starts 3..5 respectively.
- `aaaa`, i=0, j=1: the later suffix ends after three equal comparisons. There
  is no mismatch. The later suffix is a proper prefix of the earlier one and
  loses by the prefix rule; an out-of-range character must not be compared.

Some witnesses in an overlapping chain can themselves later lose; their strict
superiority still suffices to rule out the earlier start. This local lemma does
not establish an arbitrary two-pointer update formula. A candidate algorithm
must separately prove that its maintained candidates cover all uneliminated
starts, that jumps exclude only justified losers, that overlap cannot cause
self-comparison/stalling, and that boundary handling and work bounds are correct.
No such candidate-selection loop or amortized-complexity claim is implemented here.

{a,b,c} of lengths 1..6, exhausting 19,956 substrings; 13,941 suffix comparisons
supply 14,724 shifted dominance checks. These are bounded finite checks, separate
from the arguments above. No full-size benchmark, production implementation,
