## Original contract

Each listed coordinate activates one lamp; repeated coordinates do not create
extra lamps. A lamp illuminates every cell on its row, column and both diagonals,
including itself. Process queries in order: first record whether the queried cell
is illuminated, then switch off lamps in its clipped 3×3 neighborhood. Return one
integer 0/1 per query. Illumination is not the same as having a lamp in the cell.

The board side n is 1 through 10^9. Lamp and query arrays independently contain
0 through 20,000 coordinate pairs, each in bounds. An empty query list is valid.
Official examples return `[1,0]`, `[1,1]`, and `[1,1,0]`; their exact inputs and
executed oracle results are retained in `example-checks.json`.

- Python3: `Solution.gridIllumination(self, n: int, lamps: list[list[int]], queries: list[list[int]]) -> list[int]`.
- TypeScript: `gridIllumination(n: number, lamps: number[][], queries: number[][]): number[]`.

The original input is sparse coordinates, not a supplied matrix or counter table.
Both official templates are preserved unchanged in the access wrapper.

## Direct independent examples

`check-examples.py` keeps a set of active coordinate pairs. For each query it
scans that set for equal row, equal column or equal absolute coordinate difference;
then removes only nearby active coordinates. This deliberately slow oracle does
not use the usual four counter maps. Its trace records witnesses before shutdown,
removed lamps and remaining lamps. It is only used with at most two lamps here.

| Case | Result | Distinguishing point |
| --- | --- | --- |
| n=1, lamps `[[0,0],[0,0]]`, query `[0,0]` twice | `[1,0]` | Duplicate input is one active lamp; query precedes shutdown |
| n=5, lamps `[[0,0],[0,4]]`, queries `[[0,0],[0,2]]` | `[1,1]` | Removing one lamp must not erase another lamp's contribution to their shared row |
| n=3, lamp `[0,0]`, queries `[[1,1],[2,2]]` | `[1,0]` | Corner-adjacent lamps are switched off too |
| n=6, lamp `[0,3]`, queries `[[2,5],[0,3],[2,5]]` | `[1,1,0]` | A negative row-minus-column diagonal is legitimate |
| n=5, lamp `[0,4]`, queries `[[2,2],[4,0]]` | `[1,1]` | Opposite diagonal and distant lamp survival |
| No lamps / no queries | All zeroes / empty result | Both empty arrays are allowed |

The large-coordinate case uses only two lamps; it checks coordinate semantics,
not maximum-list performance. `typescript-key-check.json` separately executes a
JavaScript numeric-key collision: for n=10^9, row=999999999, columns 999999998 and
999999999, `row*n+column` is not safe as a Number identity. This does not affect
row/column or row±column keys, which remain exact in this range. Future source
must choose and explain a collision-free coordinate identity; this note does not
prescribe its representation.

## Provisional review questions

A board-sized allocation cannot represent n=10^9 practically. If summaries of
illuminating lines are introduced, explain why a count rather than a boolean is
needed, and why activating a duplicate or deactivating an already absent lamp
must not change any count. Four line tests can overlap; the answer remains one
boolean, not the number of witnessing lines. Nonzero truthiness is unsafe if a
bug allows negative counts. Each actual removal must update every summary once.

A teaching trace should distinguish query-before-removal, active lamps, illuminated
cells and the shutdown neighborhood. Back/reset must restore both the lamp set
and any derived summaries. A displayed small board is a projection of sparse
state, not the full input-limit strategy. Explain both diagonal identities and
boundary clipping concretely. State average hash-table assumptions if claiming
linear work in the number of lamp/query entries, and distinguish answer storage
from working space and saved visualization history. These are later review risks,
not source supplied to an author prompt or a claim that a lesson was validated.
