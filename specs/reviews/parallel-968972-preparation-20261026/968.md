# #968: statement, interface and teaching preflight

[Official problem](https://leetcode.com/problems/binary-tree-cameras/).
[Saved official payload](968-official-access.json); [dispatch gate](README.md).

**Verified original input/output.** Input is a binary-tree root with 1–1000 nodes;
every node value is 0. A camera can be placed at a node and covers that node, its
parent and immediate children. Return the minimum camera count covering the whole
tree. Official Python3: `Solution.minCameraCover(self, root: TreeNode | None) -> int`,
with the supplied `TreeNode` definition; TypeScript uses `TreeNode | null` and a
number result. The nullable callable annotation does not change the nonempty-tree
statement constraint.

Official level-order examples: `[0,0,null,0,0] -> 1` and
`[0,0,null,0,null,0,null,null,0] -> 2`. Keep those serialized arrays and their actual
child relationships intact when reconstructing a teaching tree. Do not infer the
structure from all-zero values or treat the array as a binary-search-tree order.

**Teaching risks and proposed questions (not a supplied proof):**

- Give nodes stable diagram identities separate from their equal input value 0.
  Preserve the original root/child structure visibly; a `null` is an absent child,
  not a node needing a camera. Explain coverage with an actual placement before
  introducing state labels. A grandchild is not automatically covered.
- If using a three-state postorder account, distinguish “has a camera”, “covered
  without a camera” and “still needs parent coverage”. Define what each state
  guarantees about the rest of that subtree before merging child states. A colored
  node alone cannot communicate either state meaning or the number of cameras used.
- A locally plausible placement is not a minimum proof. Require an explicit
  exchange/necessity or DP argument showing which unresolved need forces a choice,
  why a parent can resolve it without losing coverage, and which already-settled
  descendants remain covered. Do not assume one successful example proves optimality.
- Handle the root separately: it has no parent to satisfy a remaining need. A
  one-node tree, chains and branching trees should reveal root/leaf/null mistakes.
  The null-child state must not create a fictitious camera or uncovered real node.
- Separate finalized traversal state from temporary display focus, explain the
  traversal order, and preserve witnesses/counts during undo and locale switching.
- A 1000-node skewed input makes Python call-depth assumptions worth checking.
  Any tiny camera-subset oracle or diagram cap needs an explicit teaching bound,
  separate from official constraints and the actual submission's traversal cost.

No tree parser, visualization, recurrence, greedy proof or test oracle has been
implemented by this preparation. Original-input handling and every claimed state
invariant remain author work followed by independent verification.
