Visual-to-Python mapping: DI's fourth UI cell is I,j=1 with old [1,0], source k=0 and value 1. In Python, j=0 writes zero then adds dp[0]=1; j=1 writes that 1 before adding dp[1]=0. For IID's D row, nxt starts [0,0,0,0]; j=2 adds old dp[2]=1 and writes 1, then j=1 adds 0 and writes 1, then j=0 adds 0 and writes 1. The final rank m remains zero. Reads always use old dp, so writing nxt cannot corrupt future dependencies. Lists are local, a new list is allocated per row, the input string is immutable, and no caller state is mutated.

The invariant and inverse construction are sound: remove final j, lower labels greater than j, recover exactly one old standardized order. Relabeling and appending reverse this; I excludes k≥j and D excludes k<j. Initial [1], empty source ranges, disjoint final ranks, finite n row iterations, and addition modulo the prime justify boundaries and termination. The prime property itself is unnecessary; only modular addition is used.

Cost audit: m grows from 1 to n. Each canonical row allocates m+1 cells and traverses O(m) indices; the simultaneous old/new lists use O(n) space. Total time is O(n²), including the last O(n) sum. The baseline generates permutations lazily with O(n) auxiliary storage and an O(n·(n+1)!) upper bound including tuple generation/checks. Direct rank resummation takes O(n³). Core snapshots copy O(i²) cells for O(i) events in row i, summing to O(n⁴) time/storage if generalized; the UI explicitly limits presets to length four and distinguishes this table from runtime memory.
