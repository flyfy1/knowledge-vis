# LTI step 2 audible comparison — independent design gate

**Verdict: proceed with the bounded design below. P0: none. P1 constraints below must be implemented and verified; this is not implementation or audible-quality acceptance.** Source-first review of actual `lti/app.js`, S2 HTML/state and workflow; no browser and no product edits. The review follows the corrected proposal: 515 repeats, gain0.03, default volume50%, optional same-position10ms audition crossfade.

## Necessity, model and placement

The user explicitly requested listening at `/lti/#step2`. Put one compact comparison panel beside/below the existing S2 input-output result, with Play input / Play output / Stop and one shared volume. Reuse SIG2 and existing `runSystem` with current `s2.sys/a`; do not synthesize output from the truncated h display or add another filter model.

515 complete repeats of the existing28-point pattern give14420 input samples (1.8025s at8000 samples/s). Append512 input zeros *before* running the system; total14932 samples =1.8665s. MA3/difference have finite tails; the accumulator's512-sample tail is a truncation, not mathematically complete silence (0.95^512≈3.93e−12). The original first28 model outputs must match existing S2 exactly; the later repeated-pattern response retains previous state rather than resetting each28 samples.

This is an explicit audition mapping of abstract n to sample time, not a claim the original picture had a physical8000Hz timebase, nor a room recording. Buffer sample rate must actually be8000; if the AudioContext/device rate differs, permit its resampling without changing the declared buffer timing. Pattern repetition contributes an approximately285.714Hz fundamental and harmonics; do not call the comparison a universal characterization of every sound.

## Required guardrails

1. **Gain/data fidelity.** Use one fixed0.03 gain for all three systems and input, then user volume; no per-clip normalization, DC removal, hidden filtering or dynamically normalized plots. Independently evaluated source recurrence gives MA3 peak0.533333, diff2, acc maximum≈3.87520095 over the supported range; scaled peaks≈0.016,0.06,0.116256. Two simultaneous voices have conservative triangle bound≈0.232512<0.25. Still validate every generated finite buffer/peak at runtime; a future expanded a range must fail visibly rather than silently clip. This is a digital-level constraint, not an acoustic-volume guarantee.
2. **Audition envelope.** Apply identical8ms attack/release to playback copies *after* obtaining raw input and raw `runSystem` output. Keep the56-point comparison raw and label it accordingly. The listened-to windowed pair is not exactly the output of filtering the windowed input; disclose the short click-reduction fades instead of claiming sample-perfect audible LTI identity at the ends.
3. **Time/plot honesty.** First56 samples cover only7ms. Show them as a static prefix or an explicitly labelled moving window. Do not cycle a1.8665s playhead over those56 points, or compress elapsed audio time onto that sample-index axis. A separate whole-clip elapsed/progress control can use `AudioContext.currentTime`; stopped/suspended/unavailable state must not advance a fake playhead.
4. **Parameter edits.** Same-position updates are acceptable only as an explicitly described audition crossfade between two independently zero-initial, fixed-parameter full-clip outputs. They are not a true changing-coefficient system or its transient. Preserve one master timeline; compute the new full output then start it at the current buffer offset. State/labels should distinguish current selection, pending audition update and sounding mode. Changing filter parameters during input audition need not rebuild the unchanged input.
5. **Rapid changes.** Do not hard-disconnect a nonzero fading voice merely to enforce the two-voice limit. Prefer coalescing the newest request while a10ms fade finishes, then crossfade at the then-current master offset. This keeps at most two voices, bounded update latency and no hard truncation caused by rapid sliders. A simpler explicit Stop/replay design would also be scientifically valid; no requirement for live coefficient simulation is introduced.
6. **Lifecycle.** Button play begins a fresh finite clip, never autoplay/loop. Stop, pagehide, hidden page, leaving S2/hash navigation cancel pending requests and retire audio/RAF; returning never resumes sound. End races and delayed resume promises must not resurrect an obsolete voice. Close obsolete contexts/disconnect ended sources. Gesture-triggered unavailable/resume-denied/suspended states must be explained with a retry action rather than a false playing indication. Volume changes should ramp briefly to avoid clicks; volume0 is muted, not a new waveform normalization.

## Minimum acceptance before release

- Mathematical fixture: all66 native a values0.30…0.95, all3systems, correct lengths, first28 agreement, continuation across28-boundaries, nonzero accumulator tail, gain/overlap bounds; raw56 plots use one common scale.
- Audio/render scheduling: real Web Audio or OfflineAudioContext evidence for sample rate, duration, envelopes, parameter same-offset crossfade, rapid edits/two-voice limit, no unexpected sources; test no numerical clipping. Do not infer audible timbre from DOM assertions alone.
- Actual listening by an independent operator: input/output audibly different for MA3/acc/diff at ordinary device volume, no obvious clicks or old clip after edits. Digital peak checks do not establish useful audibility; no hearing/learning outcome claim.
- UI: native keyboard and touch at390/320 desktop, min48px/3px focus, bilingual explanation and system/a labels, one original/output status, reduced motion static progress alternative, Stop/leave/Back/repeat/volume0/max, suspended/denied/no-Web-Audio fallback and no autoplay.

Scope stays S2 + bounded spec/tests and only a narrowly justified shared sound convention. No other step playback, microphone/network asset, new curriculum, persistence, quiz tracking, graph or general DSP engine.

API timing reference: [W3C Web Audio specification](https://www.w3.org/TR/webaudio-1.1/#dom-audiobuffersourcenode-start) (current Working Draft, consulted for buffer-source timing semantics; no conformance claim). Parent implementation/browser/listening evidence is still future at this gate.
