# Independent design review: static LeetCode version directories

Date: 2026-10-25. Scope: the owner's approved physical `/leetcode/<id>-codex/` and separately authored `-claude/` versions, without badges, query-based attribution or an SPA. Read the website-design and codebase-design skills, current root/collection/shared source, publisher, 120-row registry, publication records and #2916 history. No implementation, deployment or Pi mutation performed.

**Verdict: build the static publication adapter, with the P0 constraints below.** The reader's job is to open/share a version whose creator is visible in its path. This belongs in existing lesson navigation and publication. The highest-return slice is one real Codex directory per proven original, working legacy deep links, and unchanged lesson behavior. It does not require a model platform or new visible identity treatment.

## P0: smallest adequate contract

- Keep canonical numeric source directories, accepted lesson trees, solutions, reviewed registry metadata and independent scores unchanged. A single deterministic builder module should accept validated source runtime files plus explicit provenance/route identity and return a path-to-bytes payload/manifest. Both one-time migration and the existing publisher call this interface; test the same interface. It must reject unsafe/duplicate destination paths and unexpected file kinds and reuse existing runtime-only exclusions. Tests, provenance captures, review evidence and drafts must not become runtime output.
- Prefer generating physical version directories into release staging and the actual static publication root. **Do not track 120 duplicate runtime trees by default.** Static hosting needs physical deployed files, not a second editable Git source. Tracking the small builder/route manifest and reproducible receipt is sufficient; if checked-in generated output is nevertheless chosen, require a regeneration-equality check and prohibit hand edits. The shared builder earns its locality by removing migration/publisher divergence.
- Copy runtime bytes unchanged into `<id>-codex/`; the sibling directory has the same depth, so `../common.js`, shared CSS, local assets/downloads and `../../` links retain their intended resolution. Do not add `<base>`: it can redirect fragment-only navigation and downloads back into the numeric route. Explicit numeric cross-lesson links can go through retained redirects; rewriting every lesson is unnecessary. Verify actual CSS/import/download paths and cross-links, including non-LeetCode links.
- Numeric **deployed** `index.html` becomes a small static redirect document, not the canonical source file. Use a fixed sibling destination with `location.replace`, carrying `location.search` and `location.hash` exactly; no user-supplied destination. Keep `/id/` and `/id/index.html` working, avoid Back-button loops, and include a visible bilingual fallback anchor. A fixed no-JavaScript fallback cannot promise arbitrary query preservation; document that narrow limit rather than use a competing immediate meta refresh that drops URL state. Keep old numeric runtime assets as active compatibility files for cached clients; do not delete them during this migration.
- Root and collection render the explicit ready Codex destination for their title/open links, with one card per problem and unchanged numbered headings, official links, ordering, search, locale and history behavior. Route identity is separate from the reviewed registry. For `file:` links use the generated `index.html` when a generated preview exists; canonical source previews must remain usable through an explicit source-preview arrangement, not silently link to absent generated directories.
- Keep the untracked `leetcode/780-claude/` untouched and unadvertised. Directory existence and a suffix do not establish readiness/provenance. Do not include it in a broad glob or publish it. Add a ready alternative only through separately reviewed explicit metadata and actual artifact checks; an empty generic variant-management system is unnecessary now. No UI badges or guessed model names.

## Publication, cache and receipt requirements

Use the actual paused clean campaign boundary and existing checkout/runner/release ownership. Keep the goal paused. Require no pending old release before migration. Preserve the registry bytes and all historical release records; their original numeric public hashes remain truthful historical receipts. Record a separate migration receipt with source revision, per-lesson accepted candidate/source digest (or documented legacy source), builder version/hash, generated path/hash map, redirects, discovery files, target and verification result. Generated payload identity is distinct from acceptance identity.

Modify future publisher **payload construction and verification**, retaining the existing independent acceptance gate and original source digest. New pending records must bind the actual generated files; recovery must replay those exact staged bytes. Preserve compatibility with existing receipt/pending formats rather than reinterpret or silently regenerate old records. Deploy the reviewed publisher to its actual central checkout at a safe saved-head transition before future releases, so a later ordinary batch cannot restore numeric HTML or omit new version assets. This does not authorize resuming the queue.

Publish and verify every new version asset before switching numeric redirects and discovery links; retain durable pending/recovery evidence for partial failure. Update root/collection cache references when their scripts change. Inspect ordinary URL cache behavior: stale numeric HTML may still display the old lesson instead of redirecting, and stale root/collection scripts may still point there. Retaining old assets prevents breakage but does not prove immediate path migration. Test an existing browser session as well as a fresh one, and report any remaining cache delay. Do not weaken public hash checks to accommodate cache failures.

Before success: exact copied-byte parity for every emitted runtime; redirect tests with query, encoded values and fragment; actual `/id-codex/` and `/id-codex/index.html` pages; legacy navigation and Back; both languages; root/collection search/IME and count; a real solution download; cross-lesson anchors; zero missing assets/errors. The publisher's current browser gate hardcodes numeric paths: extend it to assert final version paths and separately exercise legacy redirects, while retaining its existing IDs/official-links/bilingual-content checks. Verify all generated public hashes and all migrated lessons' basic navigation. Narrow/keyboard smoke checks ensure unchanged visible UI remains usable. No new CSS, tokens, animations, analytics or network dependencies are needed.

## P1, P2 and deferred

**P1:** ready alternative links only when a separately reviewed Claude artifact exists; provenance/route metadata must not duplicate problem cards. **P2:** none for this request. **Deferred:** badges, model comparisons, automatic directory discovery, server routing infrastructure, and tracked runtime duplication; these add maintenance without improving the requested shareable URL. If scope can be limited by the owner, publishing only physical #780 versions first is the smaller valid route, with the same redirects/provenance checks; it is not a reason to silently narrow an all-originals migration.
