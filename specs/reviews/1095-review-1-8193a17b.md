### Correctness, values, and cost

- **Peak invariant:** p belongs to closed [lo,hi]. If a[m]<a[m+1], strict mountain ordering proves m<p; otherwise p<=m. Thus lo=m+1 or hi=m preserves p and strictly shrinks the interval. When lo<hi, floor midpoint is below hi, making m+1 in bounds. The singleton terminates peak search.
- **Search invariant:** the current side's matching position, if any, remains in [lo,hi]. Increasing and decreasing halves have opposite exclusion directions; equality is tested first. All discarded positions cannot match. Inclusive search terminates when lo>hi. Strictness ensures at most one match on each side, and every left-side position is earlier than every right-side position. Searching left first proves minimum index. Neither invariant incorrectly asserts all target positions survive across both phases.
- **Before/after mapping:** smallest preset op1 reads a[1]=4 and a[2]=2, updates old [0,2] to [0,1]; Python lines 8–11 compare get(mid)<get(mid+1), then execute `hi=mid`. Op4 has increasing [0,1], mid0, value1<target2 and executes `lo=mid+1`, producing [1,1]. Op5 checks equality before value4>2 causes `hi=mid-1`, producing empty [1,0]. Phase change then initializes [peak+1,n-1]=[2,2]. The trace's separate equality and return frames represent the same Python return with no extra get. Renderer snapshots are explicitly post-comparison or phase-change, consistent with markers and old/new logs.
- **Independent custom code checks:** imported and executed the actual `leetcode/1095/solution.py` via importlib with a bounds-checked counted get mock. Predictions already recorded above were confirmed: [2,7,11,9,5,1], target9 ->3 (8 gets), target7 ->1 (5), target8 ->-1 (8); [2,6,10,6,1], target6 ->1 (5). The target9 access sequence was (2,11),(3,9),(1,7),(2,11),(1,7),(2,11),(4,5),(3,9). Thus the descending comparison at index4, 5<9, excludes [4,5] and retains index3. Inputs stayed equal to the original values; the submission contains no setter, sorting, copied array, or cache. Invalid plateaus and monotone arrays are correctly excluded by the input guarantee.
- **Cost proof:** peak interval size at least halves each round, requiring <=ceil(log2 n) rounds with two gets each; each closed side search uses <=floor(log2 n)+1 rounds with one get each. At n=10000 these safely bound 28+14+14=56 gets, below100. The loops are sequential, so O(log n) time/get calls and a fixed set of scalar variables gives O(1) auxiliary space.
