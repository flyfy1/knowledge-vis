The proof and actual code agree: positive equal binary values have identical significant strings and therefore equal one counts. Grouping k ones fixes all three starts. The third string ends at n, fixing L. The two fit inequalities prevent earlier strings from crossing the next group's first 1. If all L columns match, each earlier string contains k ones (as the third does), so gaps have no extra ones; remaining zeros can lead the next part. Thus constructed parts are nonempty and equal. A failed inequality or column rejects every possible positive solution. Zero and indivisible-count branches precede start detection. Termination follows the finite scan and finite `range(length)`.

Concrete visual-to-code transition: Tail at state 2/5 has checked d=0, bits 1,1,1, confirmed prefix length 1. At 3/5, `offset=1` reads arr[1],arr[4],arr[7]=0,0,0 and leaves the failure condition false, extending the confirmed prefix to 2. In the mismatch preset, d=1 instead reads arr[1],arr[4],arr[7]=1,0,0 and immediately returns [-1,-1]. The digit row is original input with fixed index labels, not a changing algorithm-state array. The orange ledger border and explicit “just completed” text identify the current completed operation; cyan button focus does not redefine that operation.

Canonical cost: one sum, one start-finding scan, and at most n aligned comparisons give O(n) time. Fixed scalar counters/indices and range iteration give O(1) auxiliary machine words; arr is never mutated. The baseline has Θ(n²) possible cuts and O(n) digit updates per attempted cut in the worst case; slicing and unbounded integer arithmetic make it unsuitable at maximum n. The lesson explicitly qualifies digit-update versus bit cost. JS simulation allocates positions/frames/history separately and does not claim Python's space bound.
