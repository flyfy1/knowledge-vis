# #1172 Dinner Plate Stacks

Official source: https://leetcode.com/problems/dinner-plate-stacks/
The retained ordinary public response is HTTP 200, Hard, free, with full content
and language templates.

## Original class and semantics

Python3 class `DinnerPlates` exposes `__init__(self, capacity: int)`,
`push(self, val: int) -> None`, `pop(self) -> int`, and
`popAtStack(self, index: int) -> int`.
TypeScript class `DinnerPlates` exposes `constructor(capacity: number)`,
`push(val: number): void`, `pop(): number`, and `popAtStack(index: number): number`.
The official operation example represents construction and void pushes by null;
these are distinct from the integer -1 returned by unsuccessful pops.

Stacks have fixed indices 0, 1, 2, ... and equal capacity. Push uses the lowest
index whose stack is not full. Pop uses the highest index whose stack is nonempty.
Both removals take the top element; popAtStack touches only its specified stack
and returns -1 when that stack is empty. There is no rollover or shifting of
plates from neighboring stacks to fill a hole.

Capacity and pushed value are each 1..20,000; the popAtStack argument is
0..100,000. At most 200,000 calls total are made to push, pop and popAtStack.
The conceptual stack row is infinite: an index beyond currently materialized
storage is an empty stack, not an invalid official request. Negative indices
are outside the contract. No allocating all intervening stacks is required for
an unsuccessful far-index pop. Values are positive, so -1 is unambiguous.

## Hand traces and independent scan model

Seven traces contain 66 hand-written return values and complete expected states,
including the entire official operation sequence. Array positions are stack
indices; entries inside each stack are bottom-to-top. The reference scans the
list left-to-right for push and right-to-left for pop; it uses no heaps, ordered
sets or optimized candidate structure. Each hand state is checked against that
scan model with both retained and trimmed empty tails.

| Entirely empty | pop(), popAtStack(100000) | Both -1, no value/state change |
| Repeated values | push(7), push(7), pop(), pop() | Two separate values removed, both 7 |
| Capacity upper bound | Capacity 20,000 with two pushes | Both remain in stack 0; ordinary LIFO |

Tail trimming removes only represented empty stacks after the rightmost nonempty
one. It does not renumber any remaining stack. Observational equivalence follows
because pop ignores those empties, popAtStack sees them as empty either way, and
push recreates the smallest omitted index only after all lower indices are full.
An interior empty stack cannot be erased: later nonempty stack indices would
change. The hand traces verify these distinctions on actual operations; they do
not establish a full optimized implementation's correctness or performance.

## Concrete obligations if a future implementation uses lazy heaps

No heap is implemented or certified here. A semantic stack index is not the same
thing as a heap entry naming that index. The following obligations arise directly
from the recorded state transitions:

- After filling a hole, its previous availability entry may still exist. Before
  using an entry for push, verify that the referenced current stack has room, or
  is exactly the valid next omitted stack under the chosen representation. A
  stale full-stack entry must not cause overflow or skip an earlier real hole.
- Repeated popAtStack/push cycles can produce duplicate entries unless the chosen
  design prevents them. A duplicate must not be treated as a second stack slot;
  validity must be checked again after each mutation.
- After tail removal, an old entry can refer beyond current storage. It must not
  be dereferenced blindly. A later push can recreate the same semantic index,
  so prior invalidity is not permanent; cleanup/bookkeeping must agree with the
  current stack state. This does not prescribe generation tags or any one design.
- An entry for a previously nonempty stack may remain after it empties. Pop must
  still choose the greatest currently nonempty index, skipping holes. If tails
  are retained, the last allocated slot alone is not a nonempty certificate.
- Removing one valid candidate must not accidentally erase knowledge of another
  eligible index. A chosen data structure must prove that cleanup terminates and
  that every eligible lowest/highest index remains discoverable.

These are future proof/review requirements, not reproduced defects attributed
to a live lesson. No production complexity, 200,000-operation workload, UI
rendering, author prompt adoption or independent learner acceptance is claimed.
