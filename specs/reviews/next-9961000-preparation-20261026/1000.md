## Original contract and interfaces

Piles lie in a row. Each move merges exactly `k` consecutive **current** piles
into one, costing their total stone count. Minimize cumulative cost to leave one
pile; return `-1` if impossible. Length is 1–30, each pile contains 1–100 stones,
and `2 <= k <= 30`. In particular, the original contract does **not** require
`k <= n`. No move is necessary when the input already has one pile.

- Python3: `Solution.mergeStones(self, stones: list[int], k: int) -> int`.
- TypeScript: `mergeStones(stones: number[], k: number): number`.

Official cases: `[3,2,4,1], k=2 -> 20`; the same row with `k=3 -> -1`;
`[3,5,1,2,6], k=3 -> 25`. Templates and metadata are saved verbatim.

## Independent tiny examples

The oracle recursively enumerates every legal next contiguous merge in the
literal current row, retaining one minimum-cost history. It uses neither a greedy
choice nor the interval-DP recurrence that a lesson might teach.

| Original teaching input | Minimum | What it distinguishes |
| --- | --- | --- |
| `[6,4,4,6], k=2` | 40 | Cheapest adjacent pair first costs 8+14+20=42; merging the outer pairs costs 10+10+20=40 |
| `[1,100,1], k=2` | 203 | The two ones are not adjacent; merging arbitrary smallest piles would violate the contract |
| `[7], k=30` | 0 | Already one pile; k>n is legal |
| `[1,2], k=30` | -1 | More than one pile with no legal move |
| `[1,1,1,1,1], k=3` | 8 | Every move costs the sum of its current piles, not simply the original final sum |

All three official cases are also checked. Complete minimum histories are saved
in `example-checks.json`; this is small enumeration, not a full-constraint solver.

## Teaching and code-review risks

Each move reduces the pile count by k−1, so reaching one requires
`(n−1) % (k−1) == 0`. Explain why it is also sufficient for feasibility of pile
counts: while a compatible count exceeds one it is at least k, allowing another
consecutive merge. This says nothing about minimum cost. For n=1 the condition
passes and cost is zero, even when k is large.

A provisional direction is interval DP because current piles each represent
contiguous blocks of the original row. A transparent state can ask for the cost
to reduce an interval to exactly p piles. A compressed two-dimensional state needs
to state how many piles it represents: the interval length's remainder determines
the minimum reachable count `1 + (length−1) % (k−1)`. That state is not always the
cost of one pile. For k=3, a length-2 interval can have zero cost while still
representing two piles. Distinguish this valid zero-cost partial state from an
unreachable state initialized to infinity.

If reducing k piles to one, add the interval sum once at that final operation.
Adding it at every split overcharges; omitting it undercharges. Justify any split
stride k−1 through the reachable number of piles on each side rather than treating
it as a speed trick. Prefix sums measure total stones in a block, not previous
merge costs. Show why an optimal split permits optimal subproblems, and distinguish
a candidate split from a completed merge that earns a cost. These are provisional
verification prompts, not a mandated state representation or supplied lesson proof.

Preserve both current pile weights and their original contiguous index spans.
After a merge, adjacency refers to the new row; internal piles cannot be selected
as though still independently available. Positive stones mean operations cost
something, but the answer can be zero for one pile or -1 when impossible. Treat
infinity as a sentinel internally and convert only the final infeasible result.
Do not silently replace k with 2, restrict inputs to k<=n, reorder the row, or use
unrestricted Huffman merging.

Actual complexity depends on whether the implementation uses explicit p states,
compressed states, split strides and memoization. Count all state transitions
and distinguish prefix-sum storage from trace/history storage; no performance
claim is established here. A useful trace contrasts a tempting local merge with
the optimum, displays cumulative cost separately from pile weight, and explains
why an impossible pile count cannot be rescued. No implementation or author
prompt adoption is performed by this preparation.
