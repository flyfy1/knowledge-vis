# Atlas runtime split, concept search index and essay concepts

Claude Code (claude-opus-5-5), 2026-11-11. Owner's goal: "whenever there is something I don't
understand, I can come here, click once and see a visualization of it". This spec covers what the
atlas loads, how search ranks, the concept index the homepage uses, and how essay pages add concepts.

## Why

A survey found four gaps, each verified before this change:

1. `atlas/data.js` (312,552 bytes) + `atlas/questions.js` (146,093) = 458,645 bytes, over the build's own
   450,000-byte gate. The gate only printed a warning; nothing could be added cleanly.
2. Atlas search was a substring match on title and description; the validator knew an `aliases` field
   but no node had one and search ignored it.
3. The homepage search covered page title, description and tags only. A concept that is a step or
   chapter inside a page (e.g. "Eigenvectors" in the eigen page) could not be found by its own name.
4. The atlas titled itself "Mathematics & Physics" although it has ten regions.

Measured composition of the old payload: node descriptions 78 KB, edge reasons 78 KB, edge labels 20 KB,
question prompts 65 KB, question reveals 38 KB. The first paint needs none of these except for the one
selected concept: the map and list need titles; the question list needs question titles.

Atlas files are generated by `scripts/build-atlas-data.cjs`; search files (`search/manifest.js` + `search/chunks/*.js`) are generated independently by `scripts/build-search-index.cjs` so search growth never blocks atlas or essay registration. Detail files carry a
content hash in their URL (`details/math.edges.js?v=<sha1>`), listed in `atlas-index.js`; they need no
cache-key bump. An edge appears in the edges file of both endpoint regions, so one concept's detail needs
exactly one `nodes` + one `edges` file.

`atlas-index.js` stores rows compactly and expands them to the usual objects (`ATLAS.nodes[i].title`,
`.lessons[].slug/.primary`, `ATLAS.edges[i].from/.to/.id`, `ATLAS.questions[i]`) when it runs, so app.js
code reads the same shapes as before; details are merged into those objects by `ATLAS.addDetails`.

**Investment atlas** (`--graph investment/atlas/graph`) is unchanged: one complete `data.js` with no
`chunks`; app.js treats every region as loaded when `ATLAS.partial` is absent.

## Limits (enforced: the build exits 1, also under `--check`)

- `atlas-index.js` ≤ **160,000 bytes** (was 150,000 until 2026-11-18; before that a 450,000-byte warning on
  data.js + questions.js). Fixed part (trails, regions, code) ≈ 23 KB; each concept adds ≈ 211 bytes including its
  share of edges and questions. Three times the 156 concepts of 2026-11-13 (468) projected to ≈ 122 KB.
  **2026-11-18, raised to 160,000 as a stop-gap:** importing the nine essays registered that day (how-a-chatbot-writes,
  what-a-frontier-model-takes, a-secret-in-public, what-quantum-computers-do, why-chips-are-hard, why-fusion-is-hard,
  why-batteries-hold-so-little, why-atoms-stick-together, why-one-rate-moves-everything; 107 concepts) brings the atlas
  to 775 concepts and the index to about 154 KB, past the old limit (153,130 bytes before their edges).
  **2026-11-21, compacted to 138,397 bytes (for 789 concepts):** `scripts/build-atlas-data.cjs` now emits a unique
  lesson-slug table `L` (`~index` for non-primary, scalar when single lesson, omitted when zero lessons) and drops the
  6-space per-row indentation in `N`, shrinking `atlas-index.js` from 155,399 to 138,397 bytes while expanding to the
  exact same `window.ATLAS` object. `UPFRONT_LIMIT` stays at `160,000` bytes.
- `search/manifest.js` ≤ **30,000 bytes** and each `search/chunks/*.js` ≤ **60,000 bytes** (enforced by
  `scripts/build-search-index.cjs`, independent of `build-atlas-data.cjs`). Previously `atlas/search-index.js`
  had a single-file 200,000-byte gate (reaching 191,319 bytes on 2026-11-12). On 2026-11-13, search was
  decoupled into `search/` and sharded per region (auto-splitting at 45,000 bytes into `<region>-1.js`,
  `<region>-2.js` if a region grows larger), removing the global ceiling.
- `data.js`/`questions.js` have no runtime limit: no page's first paint depends on them. The galaxy, a
  whole-graph view, still loads `data.js` (313 KB, 113 KB gzipped).

## What the atlas page loads

- Up front: `atlas-index.js` + `concept-search.js` (+ app/bridges as before).
- The selected concept: its region's `nodes` + `edges`. Default view (Fourier) loads
  `waves.nodes.js` + `waves.edges.js`.
- An active route: `nodes` + `edges` of its stops, `nodes` of its starting ideas.
- An open question: its region's `questions`.
- List view: `nodes` for the regions of the shown results (first 40 until "Show all").
- A search: `nodes` of every region (descriptions and aliases are searched).
- When nothing shown is waiting, the regions of the selected concept's neighbours are prefetched
  quietly, so "Explore →" renders immediately.

While a needed file is in flight the detail shows the title, the experiment buttons and "Loading the
explanation…" with `#detail[aria-busy=true]`; a failed file shows "could not be loaded" and is not
retried automatically. A re-render after arrival happens only if something on screen waits
(`[data-details-wait]`, list text, a search) and keeps the `#detailTitle` element and focus.

`ATLAS.loadDetails(regions = 'all', kinds = ['nodes','edges','questions'])` returns a promise; tests use
`await ATLAS.loadDetails()` to read the complete graph through the page.

**List view length.** The list shows the first 40 matches and a "Show all N concepts" button that focuses
the 41st. Measured page height at 390 px (zh, default view): before 30,252 px, after 7,952 px; list view at
1280 px: 13,240 → 3,320 px. Atlas JavaScript fetched by network idle (default view, incl. app code and
the neighbour prefetch): 570,716 → 369,016 bytes.

## Search (atlas and homepage)

`atlas/concept-search.js` (`window.ConceptSearch`, also CommonJS) is the one implementation.

- Fields: `titles` (concept or page name), `aliases` (what people type; page tags on the homepage),
  `texts` (description; on the homepage the one-line summary). Both languages are always searched.
- Normalisation: NFKC + lowercase, and spaces, hyphens/dashes, underscores, middle dots and apostrophes are
  ignored, so "eigen vector", "Eigen-Vector" and "eigenvector" are one query. A plural that does not match
  retries without its final "s".
- Scores: title exact 100 / prefix 80 / contains 60; the part of a title before " · " or ":" counts as a
  title (exact 95); alias exact 90 / prefix 75 / contains 55; description contains 20 (only when no title or
  alias matched). The whole query is tried first; otherwise every space-separated word must match some field
  and the record scores its weakest word − 5.
- Questions (2026-11-11): when the query as typed matches nothing, `unquestion()` drops question words and
  the rest is scored the same way, 5 below the plain words. Chinese: 为什么/为啥/怎么回事/怎么样/怎么/是什么/
  什么是/什么/如何/是不是/有没有 anywhere, plus a one-character particle only where it touches a removed word
  (会/要/能/是/的/就/都/还 after, 的/了/是/吗/呢/啊/呀 before) and a trailing 的/吗/呢/啊/呀, so "能量是什么" keeps
  能量. English: whole words what/why/how/when/where/which/who, is/are/was/were/am/does/do/did/can/could/
  should/would/will, the/a/an/it/its/I/my/me/you/your/this/that and "'s", plus a trailing work/mean/happen
  after a leading how/what/why. "什么是熵", "为什么会共振", "what is entropy", "how does photosynthesis work"
  went from no result to the concept. A query that already matches is never rewritten, so the existing
  rankings do not move. Tests: `tests/concept-search.cjs`.
- Question scaffolding (2026-11-11, gap audit): when neither the typed query nor its `unquestion()` form
  matches a record, `unscaffold()` drops the words around the content and the rest is scored 5 below the
  plain words. Built from the audit's 83 misses, not from a word list:
  - Chinese phrases: 是什么意思/什么意思/的意思/的含义, 有什么用/作用/影响/好处/意义, 起什么作用, (之间的/有什么)区别/
    不同/差别/差异, 怎么区分, 的原理/原理是什么/的工作原理, 对(身体…)的影响; 有 next to a question word
    ("为什么有白天黑夜", "质数有什么用") is a particle.
  - A predicate left as a whole word after a question word is dropped, never the first word: 意思 含义 形成
    工作 起作用 发挥作用 发生 运作 运行 产生 来 算 计算 区分 实现 看 读 定义 用 有 影响 原理 回事. "四季是怎么形成的"
    → 四季, "元素周期表怎么看" → 元素周期表; "杠杆原理", "功", "有机化学" have no question word and stay whole.
  - English: what causes / what is the cause of / what is the meaning of / what happens when / explain /
    tell me about / where does X come from / how to (calculate|read|find|use…) X / how are X made /
    what are X used for / how does X affect Y / effect of X on Y; a trailing work/function/form/occur only
    after a leading how/why/what/where/when ("loss function", "wave function" stay); and the words
    we/us/our/they/people/someone/get/have/has/had/to.
  - Strict: this fallback (and the comparison below) counts titles and aliases only, and a contained match
    must start at a word ("rent" does not match "current", "emotion" not "plate motion"); Chinese has no
    word breaks. Without this, "what causes tides" opened the integral page.
- Plurals: "-ies" → "-y" and "-sses/-xes/-ches/-shes" → drop "es" are tried before dropping "s" ("batteries").
- Comparisons (2026-11-11): `compare()` reads "A vs B", "A versus B", "A compared to B", "difference(s)
  between A and B", "compare A and B", and Chinese "A和/与/跟/同/及B" only together with a comparison word
  (的区别, 有什么不同, 差别, 差异, 怎么区分, 对比), so "酸和碱" and "和弦" stay whole; "均值vs中位数" works. When
  the whole query matches nothing for a record, each half is scored (strictly): both halves → min − 5;
  one half → that score − 10. `arrange()` (used by `rank()` and by the homepage after its own sort) puts
  what covers both halves first, then alternates the best of each half. "mean vs median" →
  mean-median-mode / numbers-lie #c8; "molecule vs atom" → molecules-atoms; a plain query is not rearranged.
- Order: score, then shorter title, then registry order. The homepage adds one tie rule for whole essays
  (specs/index-pagination.md § Search).

Atlas: the list follows this ranking while a query is active; the map keeps all concepts and marks
non-matches "Outside results" as before.

General rule for this class: an everyday word for an idea belongs to the concept (or the page tag) whose
step first shows the idea, not to a step that uses it later; a concept's anchor is the step that
introduces it, not the step with its formula. Avoid whole-question aliases that share many words with
other phrasings: under the every-word rule a partial match ("where do musical scales come from" for
"where do scales come from") scores low and blocks the fallback for that record.

**Page-level search terms.** Pages carry no alias field; `tags` are search-only by UI-I18N-SPEC
("tags 不再在首页显示，只参与全站搜索") and are scored as aliases. The smallest consistent mechanism is a
topic tag on the page entry: backpropagation (神经网络 / Neural Network, 损失函数 / Loss Function), sorting
(算法 / Algorithm), inside-a-phone (手机 / Cell Phones, 手机是怎么工作的 / How Do Cell Phones Work). A word for
an idea inside a page goes to `aliases.json` instead.

## Search index format (`window.KNOWLEDGE_CONCEPTS`)

`search/manifest.js` initializes `window.KNOWLEDGE_CONCEPTS` (v2) with `chunks` and an `add(rows)` helper;
each `search/chunks/*.js` appends its rows via `window.KNOWLEDGE_CONCEPTS.add([...])`:

```js
{ v: 2, atlas: "atlas/", regions: [[id, zh, en], ...],
  fields: ["id","region","href","titleZh","titleEn","aliasesZh","aliasesEn","summaryZh","summaryEn"],
  chunks: ["search/chunks/math.js?v=...", ...],
  concepts: [[id, regionIndex, href, titleZh, titleEn, [aliasZh..], [aliasEn..], summaryZh, summaryEn], ...] }
```

`href` is site-root relative and is the best place to see the concept:

1. the concept's `source` when it is a page on this site (e.g. `signal/transforms/fourier/#step5`); an
   anchor the page does not have is dropped (legacy `#stepN` on power-converters);
2. else its primary lesson with its `#stepN` or chapter anchor;
3. else, for a concept with only external reading, the atlas's own inline lab when a lab route contains
   it (`atlas/?trail=motion&node=oscillation`), else `atlas/?node=<id>`.

Summaries are the description's first sentence, capped at 36 characters (zh) / 96 (en).

## Aliases

Canonical shape on a node: `aliases: { zh: [..], en: [..] }` (either list may be empty, not both). The
earlier validator expected an array of `{zh, en}` pairs, but no node used it; aliases are per language, so
the validator now enforces the object shape (the build still converts a pair array). Sources, merged:

- the node itself (`core.json`, a v1 fragment's `aliases`, a v2 node's `aliases`);
- `atlas/graph/aliases.json` — `{ "<node id>": { "zh": [..], "en": [..] } }`, for adding what people type
  to an existing concept without touching its fragment. Unknown ids are reported by the build.

Write everyday phrasing, not only the textbook term ("利息" for compound interest, "bell curve" for the
normal distribution).

## Essay pages (many concepts per page)

An essay is one page with chapters `#ch1…#chN`; each chapter idea is its own concept with its own
anchor and aliases. It is a schema-2 fragment `atlas/graph/lessons/<slug>.json`:

```json
{ "schema": 2, "kind": "essay", "slug": "<slug>", "generatedFrom": "<path>/REGISTRY.json",
  "nodes": [{ "id": "…", "group": "<region>", "stage": "senior", "order": 50,
              "title": {"zh": "…", "en": "…"}, "description": {"zh": "…", "en": "…"},
              "aliases": {"zh": ["…"], "en": ["…"]}, "source": "../<path>#ch3",
              "lessons": [{"slug": "<slug>", "step": null, "anchor": "ch3", "category": "…", "stage": "senior", "primary": true}] }],
  "edges": [], "questions": [],
  "seeAlso": { "<concept id>": ["<related page slug>"] } }
```

- `lessons[].anchor` is the chapter id; the validator checks `id="<anchor>"` exists in the page.
- `relatedPages` become `seeAlso`, never edges: an edge needs a written, sourced reason. The build lists
  them in `merge-report.json` → `edgeCandidates` with the concepts that teach each related page, for an
  editor to write real relations later.
- `order` keeps chapter order inside the region.
- Edges are written by hand into the fragment after the import (from = the idea built on, to = the idea
  that builds on it; a `source` link to the chapter that makes the connection). Re-running the importer
  for the same essay keeps those edges and questions and drops an edge only when neither end is still one
  of the essay's concepts.

## Pagefind full-text search (2026-11-21)

In addition to the concept and page-title matcher (`search/`), the site ships a static **Pagefind** full-text index in
`pagefind/`, generated by `node scripts/build-pagefind-index.cjs` (`--check` in tests):

1. **Bilingual full-text extraction (`scripts/build-pagefind-index.cjs`)**:
   - Every live page (excluding the dedicated LeetCode adapter) is synthesized into both `zh-CN` and `en` HTML documents
     in a scratch directory by combining the page's markup with its translation tables (`copy.*.js`, `i18n.js`, `app.js`,
     `data-zh`/`data-en` attributes, and any parallel `variants/claude-code/<slug>/` prose).
   - Non-section `id` attributes are stripped and section/step IDs (`#chN`, `#stepN`, `#partN`) are attached to their
     headings (`h2`/`h3`), so Pagefind `sub_results` link straight to chapter and step anchors with the heading title and
     highlighted `<mark>` excerpts.
   - Chrome, navigation, controls, SVGs, canvases and provenance labels are excluded via `--exclude-selectors`.
   - `pagefind/build-manifest.json` records the page count and content signature so `--check` detects any drift.
2. **Homepage integration (`index.html`)**:
   - Lazily imports `pagefind/pagefind.js` on first search focus, typing, or `?s=` load (never on first paint) and merges
     the `zh-CN` and `en` language indexes.
   - Full-text chapter/paragraph matches (`a.card.fulltext-card`) are deduplicated against page/concept hits, scoped by
     the active category, subtopic and stage filters, and displayed with `<mark>` excerpts and chapter deep links.
3. **Site-wide search modal (`site-nav.js`, `site-nav.css`)**:
   - Every content page that includes `site-nav.js` renders a floating search button (`.site-search-fab`, bottom-right,
     48×48 px minimum tap target) and supports the `⌘K` / `Ctrl+K` shortcut to open a full-text search dialog
     (`.site-search-modal`).
