# Atlas runtime split, concept search index and essay concepts

Claude Code (claude-opus-5-5), 2026-11-11. Owner's goal: "whenever there is something I don't
understand, I can come here, click once and see a visualization of it". This spec covers what the
atlas loads, how search ranks, the concept index the homepage uses, and how essay pages add concepts.

## Why

A survey found four gaps, each verified before this change:

1. `atlas/data.js` (312,552 bytes) + `atlas/questions.js` (146,093) = 458,645 bytes, over the build's own
   450,000-byte gate. The gate only printed a warning; nothing could be added cleanly.
2. Atlas search was a substring match on title and description; the validator knew an `aliases` field
   but no node had one and search ignored it.
3. The homepage search covered page title, description and tags only. A concept that is a step or
   chapter inside a page (e.g. "Eigenvectors" in the eigen page) could not be found by its own name.
4. The atlas titled itself "Mathematics & Physics" although it has ten regions.

Measured composition of the old payload: node descriptions 78 KB, edge reasons 78 KB, edge labels 20 KB,
question prompts 65 KB, question reveals 38 KB. The first paint needs none of these except for the one
selected concept: the map and list need titles; the question list needs question titles.

All are generated by `scripts/build-atlas-data.cjs` except `concept-search.js`. Detail files carry a
content hash in their URL (`details/math.edges.js?v=<sha1>`), listed in `atlas-index.js`; they need no
cache-key bump. An edge appears in the edges file of both endpoint regions, so one concept's detail needs
exactly one `nodes` + one `edges` file.

`atlas-index.js` stores rows compactly and expands them to the usual objects (`ATLAS.nodes[i].title`,
`.lessons[].slug/.primary`, `ATLAS.edges[i].from/.to/.id`, `ATLAS.questions[i]`) when it runs, so app.js
code reads the same shapes as before; details are merged into those objects by `ATLAS.addDetails`.

**Investment atlas** (`--graph investment/atlas/graph`) is unchanged: one complete `data.js` with no
`chunks`; app.js treats every region as loaded when `ATLAS.partial` is absent.

## Limits (enforced: the build exits 1, also under `--check`)

- `atlas-index.js` ≤ **150,000 bytes** (was: 450,000-byte warning on data.js + questions.js). Fixed part
  (trails, regions, code) ≈ 23 KB; each concept adds ≈ 211 bytes including its share of edges and
  questions. Three times today's 156 concepts (468) projects to ≈ 122 KB.
- `search-index.js` ≤ **200,000 bytes**. Each existing concept costs ≈ 321 bytes; an essay concept with
  several aliases ≈ 465. 468 concepts at that mix project to ≈ 195 KB (≈ 80 KB gzipped). Beyond that,
  shard the index (e.g. one file per region, loaded in parallel) rather than raising the limit.
- `data.js`/`questions.js` have no runtime limit: no page's first paint depends on them. The galaxy, a
  whole-graph view, still loads `data.js` (313 KB, 113 KB gzipped).

## What the atlas page loads

- Up front: `atlas-index.js` + `concept-search.js` (+ app/bridges as before).
- The selected concept: its region's `nodes` + `edges`. Default view (Fourier) loads
  `waves.nodes.js` + `waves.edges.js`.
- An active route: `nodes` + `edges` of its stops, `nodes` of its starting ideas.
- An open question: its region's `questions`.
- List view: `nodes` for the regions of the shown results (first 40 until "Show all").
- A search: `nodes` of every region (descriptions and aliases are searched).
- When nothing shown is waiting, the regions of the selected concept's neighbours are prefetched
  quietly, so "Explore →" renders immediately.

While a needed file is in flight the detail shows the title, the experiment buttons and "Loading the
explanation…" with `#detail[aria-busy=true]`; a failed file shows "could not be loaded" and is not
retried automatically. A re-render after arrival happens only if something on screen waits
(`[data-details-wait]`, list text, a search) and keeps the `#detailTitle` element and focus.

`ATLAS.loadDetails(regions = 'all', kinds = ['nodes','edges','questions'])` returns a promise; tests use
`await ATLAS.loadDetails()` to read the complete graph through the page.

**List view length.** The list shows the first 40 matches and a "Show all N concepts" button that focuses
the 41st. Measured page height at 390 px (zh, default view): before 30,252 px, after 7,952 px; list view at
1280 px: 13,240 → 3,320 px. Atlas JavaScript fetched by network idle (default view, incl. app code and
the neighbour prefetch): 570,716 → 369,016 bytes.

## Search (atlas and homepage)

`atlas/concept-search.js` (`window.ConceptSearch`, also CommonJS) is the one implementation.

- Fields: `titles` (concept or page name), `aliases` (what people type; page tags on the homepage),
  `texts` (description; on the homepage the one-line summary). Both languages are always searched.
- Normalisation: NFKC + lowercase, and spaces, hyphens/dashes, underscores, middle dots and apostrophes are
  ignored, so "eigen vector", "Eigen-Vector" and "eigenvector" are one query. A plural that does not match
  retries without its final "s".
- Scores: title exact 100 / prefix 80 / contains 60; the part of a title before " · " or ":" counts as a
  title (exact 95); alias exact 90 / prefix 75 / contains 55; description contains 20 (only when no title or
  alias matched). The whole query is tried first; otherwise every space-separated word must match some field
  and the record scores its weakest word − 5.
- Order: score, then shorter title, then registry order.

Atlas: the list follows this ranking while a query is active; the map keeps all concepts and marks
non-matches "Outside results" as before.

## Search index format (`window.KNOWLEDGE_CONCEPTS`)

```js
{ v: 1, atlas: "atlas/", regions: [[id, zh, en], ...],
  fields: ["id","region","href","titleZh","titleEn","aliasesZh","aliasesEn","summaryZh","summaryEn"],
  concepts: [[id, regionIndex, href, titleZh, titleEn, [aliasZh..], [aliasEn..], summaryZh, summaryEn], ...] }
```

`href` is site-root relative and is the best place to see the concept:

1. the concept's `source` when it is a page on this site (e.g. `signal/transforms/fourier/#step5`); an
   anchor the page does not have is dropped (legacy `#stepN` on power-converters);
2. else its primary lesson with its `#stepN` or chapter anchor;
3. else, for a concept with only external reading, the atlas's own inline lab when a lab route contains
   it (`atlas/?trail=motion&node=oscillation`), else `atlas/?node=<id>`.

Summaries are the description's first sentence, capped at 36 characters (zh) / 96 (en).

## Aliases

Canonical shape on a node: `aliases: { zh: [..], en: [..] }` (either list may be empty, not both). The
earlier validator expected an array of `{zh, en}` pairs, but no node used it; aliases are per language, so
the validator now enforces the object shape (the build still converts a pair array). Sources, merged:

- the node itself (`core.json`, a v1 fragment's `aliases`, a v2 node's `aliases`);
- `atlas/graph/aliases.json` — `{ "<node id>": { "zh": [..], "en": [..] } }`, for adding what people type
  to an existing concept without touching its fragment. Unknown ids are reported by the build.

Write everyday phrasing, not only the textbook term ("利息" for compound interest, "bell curve" for the
normal distribution).

## Essay pages (many concepts per page)

An essay is one page with chapters `#ch1…#chN`; each chapter idea is its own concept with its own
anchor and aliases. It is a schema-2 fragment `atlas/graph/lessons/<slug>.json`:

```json
{ "schema": 2, "kind": "essay", "slug": "<slug>", "generatedFrom": "<path>/REGISTRY.json",
  "nodes": [{ "id": "…", "group": "<region>", "stage": "senior", "order": 50,
              "title": {"zh": "…", "en": "…"}, "description": {"zh": "…", "en": "…"},
              "aliases": {"zh": ["…"], "en": ["…"]}, "source": "../<path>#ch3",
              "lessons": [{"slug": "<slug>", "step": null, "anchor": "ch3", "category": "…", "stage": "senior", "primary": true}] }],
  "edges": [], "questions": [],
  "seeAlso": { "<concept id>": ["<related page slug>"] } }
```

- `lessons[].anchor` is the chapter id; the validator checks `id="<anchor>"` exists in the page.
- `relatedPages` become `seeAlso`, never edges: an edge needs a written, sourced reason. The build lists
  them in `merge-report.json` → `edgeCandidates` with the concepts that teach each related page, for an
  editor to write real relations later.
- `order` keeps chapter order inside the region.

### Commands for the integrator

```sh
# once per new region (category tech/economics/society → region); the category is claimed in groups.json
node scripts/atlas-import-registry.cjs --add-region tech --zh 技术与设备 --en "Technology & devices" --categories tech
# once per essay, after the page is registered live in pages.config.js
node scripts/atlas-import-registry.cjs tech/devices/<slug>/            # or .../REGISTRY.json; --region <id> to override
node scripts/build-atlas-data.cjs --concept-map && node atlas/tests/data-quality.cjs
# preview without touching the repo
node scripts/build-atlas-data.cjs --extra-lessons /tmp/frags --out /tmp/atlas-preview
```

The importer refuses (exit 1, nothing written): ids already used by another fragment or `core.json`,
missing zh/en title or description, an anchor the page lacks, an unknown region or a category without one,
and overwriting a hand-written fragment of the same slug (`--force`). It warns about missing aliases,
unregistered related pages and a page not yet registered. Existing society region: the category
`society` is not mapped by default — the integrator decides between `--add-region` and `--region society`.

## Homepage

See `specs/index-pagination.md` § Search. The homepage loads `concept-search.js` and `search-index.js` on
the first focus of, or typing into, the site search (or when the URL has `?s=`). Concept results link
straight to the anchor.
