# 操作系统是怎么和硬件说话的 {#hero}

::: strings
kicker: 计算机 · 系统 · 一篇可以动手的长文
:::

你的程序里写一句 read() 或 printf()，几微秒后数据就从硬盘、网卡、键盘那里来了。<br>可是用户程序明明碰不到任何硬件——这句话是怎么穿过那堵墙，找到对的驱动、对的设备，再把结果送回来的？ {.sub}

下面跟着一次读文件走一遍。先看那堵墙是什么：CPU 的特权级，以及用户程序唯一能走的门——系统调用，和走一次门要多少周期。再看墙那边的内核眼里，设备只是一排寄存器；设备做完事怎么喊 CPU（中断），喊得太勤时怎么办（轮询和 NAPI）；数据怎么不经过 CPU 自己搬进内存（DMA 和描述符环），又怎么防着设备乱写（IOMMU）。然后是内核怎么认出一块新设备、给它配上驱动，一次 read() 穿过文件系统、页缓存、块层和驱动时每一层花多久，最后是怎么少走几次门（epoll、io_uring）和干脆绕开内核（DPDK、SPDK、虚拟化）。**每个模型都是真东西的缩小版**：照 Intel 手册写的权限判断，照 Linux 系统调用表填的寄存器，照内核源码写的驱动匹配规则，一个按时间推进的中断与轮询模拟，以及测量论文里读出来的每一层耗时。 {.lead}

这一页由一个 AI 写成。规则取自原始资料（Intel《软件开发者手册》里 SYSCALL、IN、HLT 等指令的操作描述，Linux 内核的文档和源码，syscall(2) 手册页，Arm 可信固件文档），测量值取自几篇论文（FlexSC，OSDI 2010；Arrakis，OSDI 2014；Neugebauer 等，SIGCOMM 2018；Ren 等，SOSP 2019；Lee 等，USENIX ATC 2019；Haas 与 Leis，VLDB 2023）和 io_uring 作者的说明，每处写明来源和日期。**不同的测量来自不同年代、不同型号的机器，只能比数量级**；标着「调出来的参数」的地方是为了让模型能算而选的，正文写明它变一倍时结论移动多少。 {.note}

## 那堵墙：特权级 {#ch1}

::: strings
toc: 那堵墙：特权级
:::

用户程序碰不到硬件，不是因为它不知道硬件在哪，而是 CPU 在每条指令上都查一次「你现在是谁」：在最低的特权级上，读写设备寄存器、关中断、换页表的指令一执行就被硬件拦下，交给内核处理。 {.law}

大楼的电闸房锁着门，住户再懂电也进不去；要修电路，得打电话给物业。CPU 里也有这样一道门禁。x86 的每个时刻都有一个当前特权级（CPL），0 到 3 四档，操作系统只用两档：内核在 0 级（ring 0），应用程序在 3 级（ring 3）。Arm 叫异常级别：应用在 EL0，内核在 EL1，虚拟机监控程序在 EL2，最底下的安全监控固件在 EL3（可信固件的文档写明它从复位向量开始就在 EL3 运行，见<a href='../how-a-computer-boots/#ch12'>《电脑是怎么开机的》第 12 章</a>）。

门禁查的是三类东西。第一类是**特权指令**：x86 的 HLT（让核心停下）、往 CR3 写新页表地址，只要 CPL 不是 0，手册写的结果都是 #GP(0)，一般保护异常。第二类是**端口 I/O**：IN、OUT 这两条指令在 CPL 大于 IOPL 时，还要查任务状态段里的一张 I/O 许可位图，对应端口的位是 1 就 #GP。Linux 给用户程序的 IOPL 是 0、位图全拦。第三类是**内存**：页表里每一项有一个「用户可访问」位，内核自己的页和设备寄存器所在的地址，在用户态要么没映射、要么这一位是 0，碰一下就是缺页异常（页表见<a href='../how-virtual-memory-works/#ch3'>《虚拟内存是怎么工作的》第 3 章</a>）。

拦下以后发生什么？CPU 不会「报错退出」，它把这件事当成一次异常：停下当前的流水线，切到 0 级，跳到内核事先登记好的处理程序。Linux 看到是用户程序越了界，就给它发一个信号——#GP 和缺页变成 SIGSEGV，Arm 上执行不认识的指令变成 SIGILL——程序多半就此结束。

把表格从上往下看一遍：在应用这一列，能执行的只有读写自己的内存和系统调用；其余每一格都是一次异常。这不是操作系统的软件规定，而是硬件在每条指令上做的检查，所以绕不过去。勾上「内核给开了门」，端口和设备寄存器那两行变成能执行——门禁的钥匙始终在内核手里，它可以按进程、按端口、按地址范围发出去。这套机制叫**特权级**（privilege level），也叫保护环（protection ring）。

表里只列了七种操作。真实的规则还有更多分支：x86 的 CLI/STI 受 IOPL 管，Arm 的 WFI 等指令可以配置成在 EL0 被拦下；读内核内存的那一行，在有 Meltdown 漏洞的 CPU 上曾被推测执行越过（见<a href='../how-a-cpu-guesses-ahead/#ch10'>《CPU 是怎么猜着往前跑的》第 10 章</a>）。Arm 各异常级别的用途取自 Arm 和可信固件的文档，EL0 写系统寄存器的结果本文没有逐条对照 Arm 架构手册。 {.take}

## 墙上唯一的门：系统调用 {#ch2}

::: strings
toc: 墙上唯一的门：系统调用
:::

系统调用就是程序故意触发的一次异常：把「我要做什么」写进约定的寄存器，执行一条 syscall（Arm 上是 svc），CPU 自己切到内核、跳到一个固定入口；内核按寄存器里的编号查一张表，找到对应的函数。 {.law}

去银行柜台办事，你不能自己走进金库，只能填一张单子从窗口递进去：单子上写业务编号和金额，柜员按编号去办。系统调用的单子就是几个寄存器。Linux 的 syscall(2) 手册页列了每种 CPU 的约定：x86-64 上，编号放在 rax，六个参数依次放在 rdi、rsi、rdx、r10、r8、r9，结果回到 rax；arm64 上，编号放在 x8，参数放在 x0 到 x5，结果回到 x0。

编号查的是内核里的一张表。x86-64 的表里，read 是 {nrRead} 号，io_uring_enter 是 {nrUring} 号，内核 7.4-rc2 里最大的编号是 {sysMax}；arm64 和后来的架构共用另一张表，read 是 {nrReadA} 号。编号一旦分配就不改，这样十几年前编译的程序今天还能运行。C 库里的 read() 函数只是几行汇编：把参数挪进寄存器，执行 syscall，把 rax 里的结果交回来。

syscall 这条指令本身做的事很少。Intel 手册里它的操作是：把下一条指令的地址存进 RCX，把标志寄存器存进 R11，从一个叫 IA32_LSTAR 的模型专用寄存器里取出入口地址放进 RIP，把 CPL 改成 0，再按 IA32_FMASK 清掉标志位里的一些位（比如中断允许位）。它**不保存栈指针**，所以内核入口的第一件事是换到自己的栈。入口地址是内核开机时写进 IA32_LSTAR 的（交接见<a href='../how-a-computer-boots/#ch11'>《电脑是怎么开机的》第 11 章</a>），用户程序只能「进门」，不能选择从哪扇门进。

切换 CPU 看同一个调用：编号不同、寄存器不同，但形状一样——编号加参数放进寄存器，一条指令进门，硬件记下回来的地址，内核查表。对比一下 x86 的第四个参数：普通函数调用把它放在 rcx，系统调用却放在 r10，因为 syscall 这条指令要占用 rcx。这种「程序和内核之间的寄存器合同」叫**系统调用约定**（system call ABI），表叫**系统调用表**。

有些系统调用其实不进内核：像取当前时间这样只读不写的，Linux 把一小段代码和数据映射进每个进程（vDSO），在用户态就做完了。表的编号取自内核 7.4-rc2 的源码；arm64 步骤里的向量表偏移和 ESR 的细节本文没有对照 Arm 架构手册逐条核实。 {.take}

## 走一次门要多少周期 {#ch3}

::: strings
toc: 走一次门要多少周期
:::

进出一次内核本身只要一两百个周期，比一次缓存缺失还短；贵在它把这件事放大了：漏洞补丁让每次进出多付几百个周期，内核还会把缓存和 TLB 搅乱。所以少走门的办法只有一个：一次多带几件事。 {.law}

去柜台办一件事，排队比办事还久；一次把十件事一起办，排一次队就够了。系统调用也是这样。2010 年 FlexSC 的作者在一颗 Core i7（Nehalem）上测过一个什么都不做、只返回时间戳的系统调用：进内核 {fxIn} 个周期，出来 {fxOut} 个周期，一共 {fxTot} 个周期，比那台机器上一次缓存缺失的 {fxMiss} 个周期还短。可是他们接着发现，一次 pwrite 之后，程序要再跑多达 {fxRec} 个周期，每周期执行的指令数才恢复到原来的水平——内核用过的代码和数据把缓存、TLB、分支预测器挤掉了一部分。

2018 年以后，这扇门又变贵了。Meltdown 漏洞让用户程序有可能借推测执行读到内核内存，Linux 的补丁 KPTI 让用户态换一张几乎不含内核的页表，每次进出内核都要写一次 CR3 换回来（机制见<a href='../how-virtual-memory-works/#ch10'>《虚拟内存是怎么工作的》第 10 章</a>）。Ren 等人 2019 年在一台 Xeon E5-2630 v3（2.4 GHz）上测量：没有 KPTI 时进出一次不到 {rBase} 个周期；有了 KPTI，固定代价是 {rK0} 到 {rK1} 个周期，其中一次写 CR3 大约 {rCr3} 个周期；CPU 不支持 PCID 时每次换页表还要清空 TLB，一个小的读测试因此在 TLB 缺失上多花 {rTlb} 个周期，有 PCID 时只多 {rTlbP} 个。他们最短的读测试（{rReadNs} 纳秒）没有 PCID 时慢了 {rSlowN}%，有 PCID 时慢了 {rSlowP}%；全部测试平均慢了 {rAvg}%。另一个补丁 retpoline 让 poll 和 epoll 测试分别慢了 {rPoll}% 和 {rEpoll}%。

## 内核眼里的设备：一排寄存器 {#ch4}

::: strings
toc: 内核眼里的设备：一排寄存器
:::

对内核来说，一块网卡或硬盘就是物理地址上的一小段「假内存」：往某个地址写一个数是下命令，从某个地址读一个数是问状态。写可以发出去就走，读却要等设备隔着 PCIe 回话，所以好的驱动尽量不读设备。 {.law}

OSTEP 教科书讲 I/O 设备时用一个「标准设备」：三个寄存器，一个状态、一个命令、一个数据。驱动先反复读状态，等设备不忙，把数据写进数据寄存器，把命令写进命令寄存器，再反复读状态等它做完。老式 IDE 硬盘就是这样，它的命令兼状态寄存器在端口 0x1F7。

寄存器有两种摆法。**端口 I/O** 是 x86 独有的一片单独的地址空间，用 IN、OUT 两条专门的指令访问：键盘控制器在 0x60，第一个串口在 0x3F8，PCI 的老式配置机制在 0xCF8 和 0xCFC。**内存映射 I/O**（MMIO）则把寄存器放进普通的物理地址：开机时固件或内核给每块 PCIe 设备分一段地址（这段地址由设备的 BAR 声明，见<a href='../how-pcie-works/#ch6'>《PCIe 为什么能一代一代翻倍》第 6 章</a>），CPU 用普通的读写指令就能碰到它。今天的设备几乎都用 MMIO；Linux 的文档说，访问端口一般不如访问内存映射的地址快；在别的架构上端口函数也被翻译成内存访问。

既然是地址，为什么不像内存一样被缓存？因为读状态寄存器要的就是设备此刻的状态，缓存里的旧值毫无用处；写命令也必须真的送到设备。所以内核用 ioremap() 映射寄存器时，用的是**不缓存**的方式，每次读写都直达设备（缓存为什么平时能省时间，见<a href='../how-cpu-caches-work/'>《CPU 的三级缓存是怎么工作的》</a>）。Linux 文档还写道：在 PCI 这类总线上，写操作是「posted」的——发出去就算完，不等回音；驱动要确认写已经到达，得再从同一设备读一次。

## 设备怎么喊 CPU：中断走过的路 {#ch5}

::: strings
toc: 设备怎么喊 CPU：中断走过的路
:::

设备做完事，往一个约定的地址写一个约定的数；这次写被送到某个核心的中断控制器，变成一个 0 到 255 之间的向量号；核心停下手上的指令，按向量号查表，跳进驱动的处理函数。处理函数只做最急的那点事，其余的推迟到稍后。 {.law}

快递到了，快递员按一下门铃，你放下手里的事去开门，签收以后东西先放门口，等手上的事告一段落再拆。中断就是这个门铃。它走的路是这样的。设备那一端：PCIe 设备不再有专门的中断线，它发 **MSI**，也就是一次普通的内存写，地址在 x86 上以 FEE 开头，数据里写着向量号——地址和数据的每个字节怎么拆，见<a href='../how-pcie-works/#ch7'>《PCIe 为什么能一代一代翻倍》第 7 章</a>。根复合体看到这个地址，把它交给目标核心的**本地 APIC**（Arm 上叫 GIC）。

核心这一端：本地 APIC 在两条指令之间打断核心。核心按向量号去查**中断描述符表**（IDT），0 到 31 号留给异常（缺页是 14 号，#GP 是 13 号），设备中断用 32 号以上。如果被打断的是用户程序，CPU 先切到 ring 0、换到内核栈，保存现场，然后跳进内核的中断入口，再分发到驱动登记的处理函数。处理完要给 APIC 写一次「中断结束」，它才会送下一个同级的中断。

::: diagram dg-irq keys=dg.irq

处理函数被叫作**上半部**（top half，Linux 叫硬中断），它运行时这个核心上的其他中断往往被挡着，所以要短：确认是自己的设备、关掉设备的中断、把真正的活登记下来就返回。真正的活在**下半部**做：网卡收包放在**软中断**（softirq）里，它在硬中断返回时、或者由每个核心一个的 ksoftirqd 线程来跑；很多驱动则用**线程化中断**，把下半部放进一个普通的内核线程，可以睡眠，也可以被调度。

中断的好处是 CPU 不用一直守着设备；代价是每一次都要打断、保存、恢复，打断还会把缓存搅乱。设备来得越勤，这笔账越难看。下一章就来算这笔账。

这里只讲 x86 的 MSI 和本地 APIC 的大致路径；中断重映射（IOMMU 的一部分）、APIC 的优先级、Arm GIC 的分组和 SPI/LPI 等细节没有展开。 {.take}

## 中断、轮询和两者之间 {#ch6}

::: strings
toc: 中断、轮询和两者之间
:::

包来得稀时，中断最省：CPU 只在有事时被叫醒。包来得密时，每个包一次中断会把 CPU 全耗在「被叫醒」上，处理完的包反而越来越少。Linux 网卡驱动的办法是两者之间：第一个包用中断叫醒，之后关掉中断，一批一批地轮询，直到队列空了再打开中断。 {.law}

餐厅里只有一两桌客人时，服务员听到招呼再过去最省力；客满时，每桌按一次铃就跑一趟，服务员会在路上累死，菜一道都上不完——这时候不如站在大厅里一桌一桌看过去。1997 年 Mogul 和 Ramakrishnan 把这种现象叫作**接收活锁**（receive livelock）：包来得太快，CPU 全部时间都花在中断里，上层的程序一点也跑不动，处理完的包反而变少。OSTEP 的 I/O 一章也用了这个例子，并建议设备时快时慢时用一种「先轮询一会儿、再改用中断」的混合办法。

Linux 网卡驱动里的这种混合办法叫 **NAPI**。内核文档描述的规矩是：中断来了以后，驱动关掉设备的中断，安排一次轮询；每次轮询最多处理 budget 个包（net.core.dev_weight 默认 {weight} 个）；包没处理完就返回 budget，过一会儿再轮询；处理完了就调用 napi_complete_done()，然后才能重新打开中断。

say.napi: NAPI：包来得稀，几乎每个包都要一次中断（每次带走 {per} 个），和纯中断差不多，CPU 占用 {cpu}。
say.napiBatch: NAPI：每次中断带走 {per} 个包，被叫醒的钱摊薄了，CPU 占用 {cpu}，平均延迟 {mean}——同样的包速，纯中断已经要 {irqcpu}。
say.napiFull: 包速接近这个核心的处理极限，NAPI 每次中断带走 {per} 个包，几乎变成了一直轮询；CPU 占用 {cpu}，但没有活锁。
:::

默认是每秒 20 万个包。每包一次中断时，这个核心被占了 {pIcpu}，平均延迟 {pIlat} 微秒；换成 NAPI，每次中断带走 {pNper} 个包，占用降到 {pNcpu}，平均延迟 {pNlat} 微秒；一直轮询的平均延迟是 {pPlat} 微秒，但核心 100% 在转。包速降到每秒 1 万，NAPI 占 {pN1cpu}，纯中断占 {pI1cpu}，没有区别；升到每秒 30 万，纯中断就过了活锁的门槛（每秒约 {pLive} 千个包），平均延迟涨到 {pI3lat} 毫秒还在涨，而 NAPI 只占 {pN3cpu}。

另一个旋钮是网卡自己的**中断合并**（interrupt coalescing）：收到第一个包后先等一会儿，攒几个再发中断。每秒 1 万个包、等 50 微秒时，每秒中断从 {pI1irq} 次降到 {pCirq} 次，平均延迟却从 {pI1lat} 微秒变成 {pClat} 微秒。Intel e1000e 驱动的默认模式就在做这种权衡：大流量时每秒最多 {itrB} 次中断，低延迟的流量放宽到 {itrL} 次。存储也有同样的选择，NVMe 盘的轮询见<a href='../why-nvme-is-fast/#ch7'>《NVMe 为什么这么快》第 7 章</a>。

模拟只有一个核心、一个队列，包的处理时间固定；没有模拟包被分到多个队列和核心（RSS，见<a href='../how-a-nic-moves-packets/#ch5'>《网卡是怎么搬运数据包的》第 5 章</a>），也没有模拟软中断太忙时交给 ksoftirqd 线程的那一步。模型里被叫醒和处理是按包排队、一件接一件做的，所以过了门槛以后表现为队列一直涨、延迟发散，每秒处理的包数停在门槛上；真实的活锁里中断的优先级更高，会抢走协议处理的时间，处理完的包数还会往下掉，这一步模型没有算。 {.take}

## DMA 与描述符环 {#ch7}

::: strings
toc: DMA 与描述符环
:::

数据不经过 CPU：驱动在内存里摆一圈「描述符」，每格写着一块空缓冲区的地址；网卡收到包，自己把数据写进下一块缓冲区，再把那一格标成已用。两边各有一个只往前走的计数器，追上了就是满，满了再来的包只能丢。 {.law}

回转寿司店的传送带上有一圈盘子：厨师往空盘上放寿司，客人从另一头取走，空盘再转回厨师那里。传送带转一圈有多少盘子是固定的；客人一走开，盘子很快就全满，厨师只能停手。网卡的接收环一模一样。驱动事先分配好一批缓冲区，把它们的物理地址（准确说是设备能用的地址，见第 8 章）写进一圈描述符。每个描述符很小，e1000 网卡的文档写的是每个 {descB} 字节，默认 {rxDef} 个，最多 {rxMax} 个。

网卡是**生产者**：每收到一个包，它用 DMA（直接内存访问）把数据写进下一个描述符指的缓冲区，再写回这个描述符的状态，然后往前走一格。驱动是**消费者**：它在中断或轮询里看到已用的描述符，把包交给协议栈，换上新的空缓冲区，然后把「我已经补到这一格了」写进网卡的一个寄存器——这就是上一章说的门铃，一次不用等的写。在 Intel 网卡里，这两个位置叫 head 和 tail：head 由硬件往前推，tail 由驱动写。

::: diagram dg-ring keys=dg.ring
cap: 八格的环。实心格里已经有网卡写进来的包，空心格指着驱动补上的空缓冲区。两个计数器只往前数，下标是计数对 8 取余；生产者追上消费者整整一圈就是满。示意。
aria: 示意图：内存里的一圈接收描述符，网卡写入、驱动取走，两个计数器和门铃
prod: 网卡（生产者）：DMA 写进缓冲区，前移 head
cons: 驱动（消费者）：取走包、补新缓冲区，写 tail（门铃）

:::

两个位置怎么判断满和空？一种干净的写法是让两个计数器一直往上数、不回头，只在取下标时对环的大小取余：下标 = 计数 &amp; (N − 1)，所以 N 必须是 2 的幂；两数之差就是环里有几个包，差等于 N 就是满。32 位的计数器数到头会自然绕回 0，相减的结果照样对。io_uring 的作者在说明里写道，环的计数器就是这样的 32 位整数，一直往上数（原文 free flowing），靠整数自然绕回。下面的模型里，两个计数器故意从接近 2<sup>32</sup> 的地方开始，你能看到它们绕回去。

同一种结构到处都是：NVMe 的提交队列和完成队列（见<a href='../why-nvme-is-fast/#ch4'>《NVMe 为什么这么快》第 4 章</a>）、GPU 的命令队列、第 11 章的 io_uring。生产者和消费者在两个不同的处理器上（一个是 CPU，一个是网卡），写描述符和推计数器的先后顺序必须对，所以驱动在写门铃之前要加一道内存屏障，保证描述符先到；屏障为什么必要，见<a href='../how-cores-share-memory/#ch9'>《多个核心怎么共用一块内存》第 9 章</a>。

模型里只有一个接收环、一个核心，包的大小不变，包按泊松过程到达；真实的流量更突发，网卡还会把一个大包拆进几块缓冲区。描述符的格式每家网卡不同，这里只画了它的作用；网卡那一侧怎么提前取描述符、怎么写回，见<a href='../how-a-nic-moves-packets/#ch3'>《网卡是怎么搬运数据包的》第 3 章</a>。 {.take}

## 给设备也装一张页表：IOMMU {#ch8}

::: strings
toc: 给设备也装一张页表：IOMMU
:::

设备做 DMA 时用的地址，不该是可以随便写的物理地址。IOMMU 坐在设备和内存之间，像 CPU 的 MMU 一样按一张页表翻译设备给出的地址：每个设备只看得见内核给它映射的那几页，越界的写被拦下并报告。 {.law}

上一章里网卡自己往内存里写，写哪里由描述符里的地址决定。要是驱动有错、或者设备的固件被人改过，它完全可以写到内核的代码上去。插在雷电口上的外接设备也能做 DMA，这正是有人借它读别人电脑内存的原因，攻击和防护见<a href='../how-thunderbolt-works/#ch8'>《雷电接口是怎么工作的》第 8 章</a>。

办法和保护进程一样：加一层翻译。设备拿到的不是物理地址，而是 **I/O 虚拟地址**（IOVA）。设备发出的每一次读写经过 IOMMU（Intel 叫 VT-d，AMD 叫 AMD-Vi，Arm 叫 SMMU），它按设备的编号找到这台设备专属的一张 I/O 页表，把 IOVA 翻成物理地址；页表里没有的地址，访问被拦下，记一条错误。翻译的结果也缓存在一个 IOTLB 里，和 CPU 的 TLB 一个道理（见<a href='../how-virtual-memory-works/#ch4'>《虚拟内存是怎么工作的》第 4 章</a>）。

::: diagram dg-iommu keys=dg.iommu
cap: 两条访问内存的路。CPU 的地址经 MMU 按进程的页表翻译；设备给出的 I/O 虚拟地址经 IOMMU 按这台设备的页表翻译，没有映射的地址被拦下。示意。
aria: 示意图：CPU 经 MMU、设备经 IOMMU 访问内存，各有自己的页表

:::

驱动并不直接摆弄这张页表。Linux 给驱动的接口是 DMA 映射：驱动说「这块缓冲区要给设备用」，内核分配一段 IOVA、在 I/O 页表里登记、把 IOVA 交给驱动写进描述符；用完再撤销映射。第 10 章的测量里，一次读要做一次映射（{leeMap} 微秒）和一次撤销（{leeUnmap} 微秒）。撤销还要让 IOTLB 里的旧翻译失效，所以内核提供了「严格」和「延迟」两种失效方式，在安全和速度之间取舍。

IOMMU 还让另一件事成为可能：把一整台设备，或者设备的一部分，直接交给一个虚拟机或一个用户程序，而不用担心它借 DMA 越界——它的页表只映射了那个虚拟机或那个程序的内存。第 12 章的用户态驱动和 SR-IOV 都建立在这上面。

这一章没有模型：IOMMU 的开销取决于映射的粒度、失效的策略和 IOTLB 的命中率，没有一组可以照搬的数。中断重映射、PASID（一台设备用多张页表）和 ATS（设备自己缓存翻译）没有展开。 {.take}

## 驱动怎么认出设备 {#ch9}

::: strings
toc: 驱动怎么认出设备
:::

内核不认识任何一块具体的设备，它认识的是「描述」：PCI 设备报出厂商号、设备号和类别码，嵌入式板子的设备树写着 compatible 字符串。每个驱动带一张「我能管谁」的表，总线把设备和表逐条比对，对上了就调用驱动的 probe()。 {.law}

新生报到，学校不认识每个人，只看录取通知书上的专业代码，把人分到对应的院系；院系再自己核对材料、安排宿舍。内核也是这样分工的。第一步是**发现**：PCI 总线开机时被逐个枚举，每个设备的配置空间里有厂商号、设备号和三字节的类别码（枚举见<a href='../how-pcie-works/#ch6'>《PCIe 为什么能一代一代翻倍》第 6 章</a>）；主板上不在 PCI 上的设备由 ACPI 表描述（见<a href='../how-a-computer-boots/#ch6'>《电脑是怎么开机的》第 6 章</a>），Arm 板子则由设备树描述。每发现一个，内核就在对应的总线上登记一个 device。

第二步是**匹配**。Linux 的驱动模型文档写得很直接：设备或驱动登记到总线上时，总线的 match() 把设备的标识和驱动支持的标识比一比，对上了就把设备交给这个驱动，调用它的 probe()。PCI 的比法写在内核源码 pci_match_one_id() 里：厂商号、设备号、子厂商号、子设备号四项，每项要么相等、要么驱动写的是通配的 PCI_ANY_ID；类别码先和驱动给的掩码相与再比。所以 NVMe 驱动不用列出每家的盘，它只写一条「类别码 0x010802，掩码 0xFFFFFF」，任何自称 NVMe 控制器的设备都归它。设备树的比法写在 __of_device_is_compatible() 里：节点的 compatible 列表里越靠前的字符串匹配上，得分越高——板子可以先写自己的具体型号，再写一个通用的兼容型号。

say.stuck: 电源驱动没有加载，SD 卡控制器永远卡在延迟列表里。开机日志里会有一条「deferred probe pending」，这就是嵌入式板子上「某个设备没出来」最常见的原因之一。
say.missing: 有 {n} 个设备没有驱动：它们在总线上，内核也看得见，但没有人管，所以用不了。
:::

默认的顺序下，四个驱动把 {b1bound} 个设备绑好，显卡因为没有加载对应的驱动而闲着。换成先登记 SD 卡控制器的驱动，它第一次 probe 时被延迟，电源一绑定就被重试 {b2retry} 次，结果相同——这就是延迟 probe 的用处：驱动加载的先后顺序可以随便，依赖关系由重试来消化。整套机制叫 Linux 的**设备驱动模型**：总线、设备、驱动三样东西，加上匹配、probe、绑定三个动作。

绑定以后，驱动按设备的种类把它登记成三种样子之一：**字符设备**（按字节流读写，比如串口、/dev/input 里的键盘），**块设备**（按固定大小的块随机读写，比如 /dev/nvme0n1），**网络设备**（不在 /dev 里，叫 eth0 或 enp3s0，收发的是包）。用户程序看到的是这三种接口，看不到 PCI 号；下一章跟着一次 read() 从文件一直走到块设备。

模型只有 PCI 和设备树两种总线、一种依赖；真实的匹配还有 driver_override、动态添加的 ID、ACPI 的 _HID 和 _CID，probe 也可以异步进行。显卡驱动的 ID 表在这里故意没有加载，不是说它不存在。 {.take}

## 一次 read() 穿过的每一层 {#ch10}

::: strings
toc: 一次 read() 穿过的每一层
:::

数据已经在内存的页缓存里时，一次 4 KB 的 read() 不到一微秒：查一下、拷一份、回来。不在时，它要穿过文件系统、块层、驱动，等设备，再被中断叫回来，单是这些软件就要花好几微秒——在最快的盘上，软件已经和硬件一样慢了。 {.law}

去图书馆借书，书在前台的还书车上，伸手就拿到；不在，就要查索书号、进书库、上楼、找架子。Linux 的读路径是这样一层层叠起来的。最上面是 **VFS**（虚拟文件系统）：不管底下是 ext4、XFS 还是网络文件系统，read() 都先到这里，按文件描述符找到文件和它的 inode。接着是**页缓存**：内核把读过的文件内容按页留在内存里，按「文件 + 偏移」查找；查到了，直接拷进用户的缓冲区，事情就办完了。

查不到，就要分一页内存、让**文件系统**把「文件的第几块」翻译成「盘上的第几块」（逻辑块号，见<a href='../what-a-drive-is-made-of/#ch1'>《硬盘里到底是什么》第 1 章</a>），把这一页插进页缓存，再交给**块层**：它把请求包成一个 bio、变成一个 request，放进按核心分开的队列。最后是**驱动**：NVMe 驱动给缓冲区做 DMA 映射（第 8 章），填一条提交队列项，按门铃（第 4 章）。设备做完，发 MSI 中断（第 5 章），完成函数撤销映射、唤醒正在睡觉的进程，进程醒来把数据拷给用户。Lee 等人 2019 年在一块 Optane 固态盘上逐步测了这条路径：4 KB 随机读一共 {leeTot} 微秒，其中设备自己只占 {leeDev} 微秒，块层提交 {leeBio} 微秒，唤醒进程的那次上下文切换 {leeCtx} 微秒，拷给用户 {leeCopy} 微秒。

在页缓存里的一次读要 {rHit} 微秒，不在时要 {rMiss} 微秒，差 {rRatio} 倍；不在的那次里，软件占了 {rSoft}。换成普通闪存盘，软件只占 {rNsoft}——慢的盘把软件的开销藏起来了，快的盘把它暴露了出来。这就是这几年内核 I/O 栈一直在瘦身的原因。命中率是 90% 时，平均每次读 {r90} 微秒。用 O_DIRECT 绕过页缓存，不命中的一次是 {rDirect} 微秒；再用轮询代替中断，是 {rPolled} 微秒，代价是 CPU 在设备工作时一直空转（第 6 章的那笔账）。

页缓存还管写。**缓冲 I/O** 的 write() 只把数据拷进页缓存、把页标成「脏」就返回，内核稍后才把脏页写回盘；断电前没写回的就丢了，所以数据库要用 fsync() 逼它写下去。**直接 I/O**（O_DIRECT）每次都去盘，适合自己管缓存的程序，比如数据库，它们不想让内核再缓存一份。顺序读时，页缓存还会**预读**：看你在顺着读，就提前把后面几页读进来。

各步的数来自一块 2019 年的 Optane 盘和当时的内核，今天的数会不同；这里只看一次 4 KB 的读，没有看大块读、预读和写回。 {.take}

## 少走几次门：epoll 与 io_uring {#ch11}

::: strings
toc: 少走几次门：epoll 与 io_uring
:::

一个服务器同时守着几万个连接，要是每个连接一个线程、每次读一次系统调用，门票和上下文切换会吃掉大半的 CPU。epoll 让一次调用告诉你「哪些连接有数据了」；io_uring 更进一步，在程序和内核之间放两个共享的环，请求和结果都写在环里，一次调用可以交一批、收一批，甚至一次都不调用。 {.law}

传统的写法是阻塞的 read()：没数据时线程睡下，数据来了被叫醒，每个 I/O 一次系统调用、一次睡醒。几万个连接就要几万个线程。**epoll** 换了个问法：先用 epoll_ctl 登记你关心的文件描述符，然后调用一次 epoll_wait，内核一次返回所有已经就绪的那些，你再逐个 read()。每个 I/O 仍然要一次 read，但「等」这件事被合并了。

**io_uring**（2019 年加入 Linux）把「读」本身也合并了。程序调用 io_uring_setup 建一对环，用 mmap 映射进自己的地址空间：提交队列（SQ）由程序写、内核读，每一项是一个 64 字节的请求（读哪个文件、哪个偏移、放到哪）；完成队列（CQ）由内核写、程序读，每一项是 16 字节的结果。和第 7 章的描述符环一样，两边各推各的计数器。程序写好一批请求，调用一次 io_uring_enter 交上去，同一次调用还可以等若干个完成。如果建环时要了 SQPOLL，内核会起一个线程专门盯着提交队列，程序连 io_uring_enter 都不用调用。

io_uring 的作者 Axboe 在 2019 年的说明里给过实测：他的测试机上，一个核心做 4 KB 随机读，轮询模式每秒约 {axPoll} 百万次，用中断约 {axIrq} 百万次，老的 libaio 在 {axAio} 千次就到顶了；空操作每秒 {axNopLo} 到 {axNopHi} 百万次，他说结果大多取决于必须执行的系统调用次数。当时环最多 {axMax} 项，必须是 2 的幂。它还有一个容易被忽略的好处：数据已经在页缓存里时，请求在提交的那次调用里就地完成，不会白白绕一圈。这一章的模型叫**每次 I/O 的系统调用**模型。

模型假设每个就绪的连接正好有一个 I/O、每批都装满；真实的服务器里批量随负载变化，epoll 也有边沿触发等用法可以少读几次。io_uring 现在支持的操作远不止读写，还有网络收发、打开文件、超时等。 {.take}

## 绕开内核，以及虚拟机里的设备 {#ch12}

::: strings
toc: 绕开内核，以及虚拟机里的设备
:::

既然门票、拷贝和唤醒加起来比设备还慢，最彻底的办法就是不进内核：把网卡或固态盘的队列直接映射给一个用户程序，它在一个专门的核心上一直轮询。代价是这个核心永远 100% 忙，而操作系统替你做的那些事——协议栈、文件系统、隔离——也得你自己做。 {.law}

Arrakis 论文 2014 年把 Linux 收发一个 UDP 包的时间拆开过（Xeon E5-2430，10 Gb 网卡）：一来一回一共 {arTot} 微秒，其中收包的网络栈 {arStack} 微秒，其余是发包的网络栈、调度、拷贝和两次进出内核；接收进程正在睡觉时，总数变成 {arIdle} 微秒。他们把网卡的队列直接交给应用以后，用兼容 POSIX 的接口是 {arP} 微秒，用自己的原生接口只要 {arN} 微秒。

今天的做法有三个名字。**DPDK** 管网卡，**SPDK** 管固态盘：内核只负责一次性的设置，通过 VFIO 把设备的寄存器和 DMA 映射交给用户程序（第 1 章的「内核给开了门」，第 8 章的 IOMMU 保证它越不了界）；之后的收发全在用户态，一个「轮询模式驱动」在专门的核心上一直看完成队列，没有中断、没有系统调用、没有拷贝。SPDK 的文档说，它的基石是一个用户态、轮询模式、异步、无锁的 NVMe 驱动。**RDMA** 走得更远，网卡直接读写另一台机器上登记过的内存，对方的 CPU 都不用参与。

:::

值不值得？拿第 6 章的**中断、轮询与 NAPI** 模型来看：包速低时，一直轮询白白占着一个核心；包速高到中断要活锁时，轮询反而最省。再拿第 3 章的**系统调用开销**模型来看：每件事的工作越少，门票的份额越大，绕开内核的收益越大。Haas 和 Leis 2023 年用 8 块固态盘测过：这些盘一共能做每秒 {haasIops} 百万次随机读，按他们的 CPU 算，每次 I/O 只有 {haasBud} 个周期的预算；SPDK 用 {haasSpdk} 个线程就跑满了，io_uring 轮询模式要 {haasPoll} 个左右，用中断的 libaio 和 io_uring 开到 {haasIrqT} 个线程也只到每秒 {haasIrq} 百万次。他们的结论是，不用 SPDK 时，大约一半的核心只是在提交和收取 I/O。可他们也写道，用户态 I/O 对使用者和程序设计有很大的影响：没有页缓存、没有文件系统，多个程序也不能共用一块盘。

虚拟机里的设备是同一个问题的另一面。客户机里的操作系统以为自己在和真硬件说话，最慢的做法是让虚拟机监控程序模拟一块老网卡的每个寄存器，客户机每碰一次寄存器就陷入一次监控程序。**virtio** 改成半虚拟化：客户机知道自己在虚拟机里，用一组共享内存里的环（叫 virtqueue，和第 7 章的描述符环同一个思路）和宿主交换请求，只在需要时按一下门铃。virtio 的规范由 OASIS 维护，1.2 版在 2022 年 7 月成为委员会规范。**SR-IOV** 则让一块物理网卡或固态盘在 PCIe 上分身成很多个「虚拟功能」，每个都有自己的队列和寄存器，借 IOMMU 直接交给一台虚拟机，数据通路完全不经过宿主的软件。

这一章没有新模型。Arrakis 和 Haas 与 Leis 的数来自不同年代、不同的机器和负载，不能互相比较；RDMA 的细节和 vhost、vDPA 等折中方案没有展开。 {.take}

## 前沿在哪（2026 年 11 月） {#ch13}

::: strings
toc: 前沿在哪（2026 年 11 月）
:::

墙还在原地，变的是墙上的门：io_uring 让一次系统调用干几百件事，却因为太大太新，在 Google 的内核漏洞奖励计划里成了被利用得最多的部分；驱动开始用 Rust 写；越来越多的设备逻辑搬进用户态，内核只负责发钥匙。 {.law}

下面分三类写：已经写进规范和源码的，已经发生的，以及有利害关系的一方说的。日期都写明。

### 已经写进规范和源码的 {#h.est .sub3}

- 截至 2026 年 11 月中，Linux 主线的版本是 7.4-rc2（内核源码顶层 Makefile），最新的稳定版是 7.3.4（kernel.org，2026 年 11 月 10 日发布）。内核文档里，sysctl 项 io_uring_disabled 可以设为 0（默认，谁都能建 io_uring）、1（只有特权进程或指定组的进程能建）或 2（谁都不能建）。 {#e1}
- io_uring 的零拷贝接收已经有内核文档：网卡把包头和数据在第 4 层的边界分开，包头照常走内核的 TCP 协议栈，数据直接落进用户内存；网卡的分流规则要用户自己用 ethtool 配好。 {#e2}
- ublk 让块设备的逻辑在用户态实现：/dev/ublkb\* 上的请求经 io_uring 的透传命令交给一个用户态的服务程序，结果也经 io_uring 交回。NAPI 文档里还有一个 irq-suspend-timeout：应用用 epoll 驱动收包时，可以在这段时间里完全挂起设备的中断。 {#e3}

### 已经发生的 {#h.demo .sub3}

- Google 安全博客 2023 年 6 月 14 日：它的内核漏洞奖励计划（kCTF VRP）过去一年收到的提交里，{gShare}% 利用的是 Linux 内核的 io_uring 组件，单是 io_uring 就付了约 100 万美元；于是 ChromeOS 关闭了 io_uring，Android 用 seccomp-bpf 过滤让应用碰不到它，Google 的生产服务器上也关掉了。 {#d1}
- 2025 年 12 月 10 日的内核维护者峰会上，与会者的共识是 Rust 在内核里已经不再是实验性的（LWN 原文：“no longer experimental”）。用 Rust 重写的 Android Binder 驱动在 Linux 6.18 进入主线；到 7.4-rc2，主线里旧的 C 版 Binder 已经删除，drivers/android 下只剩 Rust 版（本文在 git.kernel.org 上核对）。 {#d2}
- virtio 1.2 在 2022 年 7 月成为 OASIS 委员会规范；1.3 版的委员会规范草案在 2023 年 10 月发布征求意见，之后是否正式定稿本文没有查到。 {#d3}

### 有利害关系的一方说的 {#h.claim .sub3}

- Google 在同一篇博客里也写道，io_uring 带来了性能上的好处，对安全问题的修复也很及时（原文：“brings performance benefits, and promptly reacts to security issues”）；但它认为这部分代码还比较新，仍有严重漏洞，所以先限制使用，同时探索怎样给它加沙箱。这是 Google 作为使用者一方的判断；限制和继续修复两条路都还在走。 {#c1}
- 删掉 C 版 Binder 的补丁作者是 Google 的工程师 Carlos Llamas。据 Hardware Busters 2026 年 9 月 19 日的报道转述，他在补丁里写道，C 版驱动积累了十五年的复杂度，维护起来非常痛苦，加新功能时还会碰上漏洞；Rust 的支持者认为它能在编译期排除一整类内存错误。这是当事人的说法，不是独立的统计。 {#c2}

接下来要看的是：io_uring 能不能在不牺牲性能的前提下被关进更细的权限里，让发行版不再整块关掉它；更多驱动（显卡、网卡）是否跟着用 Rust 写；以及用户态驱动和内核驱动的分界会不会继续往用户态那边挪。

这些事实会过时；来源和打开日期都在本目录的 BRIEF.md 里。这里不评价哪一种做法更好。 {.take}

## 程序卡在 I/O 上时问的三件事 {#ch14}

::: strings
toc: 程序卡在 I/O 上时问的三件事
:::

一次 I/O 是一条链：系统调用、内核的各层、驱动、设备、中断、唤醒。慢的时候，先问时间花在链上的哪一段，再决定是换盘、换写法，还是换架构。 {.law}

{.plain .qs}
1. **是在等设备，还是在等软件？**设备时间远大于软件时（机械硬盘、普通闪存的随机读），优化软件没多大用，要靠缓存命中和并发；设备快到微秒级时，软件那几微秒就是大头（第 10 章），这时才值得考虑 O_DIRECT、轮询和 io_uring。 {#q1}
2. **每件事带了几次系统调用、几次睡醒？**小请求一个个发，门票和唤醒会占掉大半时间（第 3、11 章）；先试着一次交一批。看 CPU 时间里「系统态」占多少，是最快的线索。 {#q2}
3. **中断是太多，还是太少？**包或请求很密时，中断太多会把核心耗在被叫醒上（第 6 章），要开中断合并或让驱动多轮询；请求很稀、又在意延迟时，合并反而会让每个请求多等。丢包时还要看环够不够撑过停顿（第 7 章）。 {#q3}

回到开头的问题。程序碰不到硬件，是因为 CPU 在每条指令上查*特权级*；它唯一的门是*系统调用*，一条指令、几个寄存器、一张表。门那边，设备只是一排*寄存器*，内核写门铃下命令，设备做完用*中断*喊它，数据自己由 *DMA* 沿着*描述符环*搬进内存，*IOMMU* 管着它能写哪里。内核按 ID 表把设备和*驱动*配对；一次 read() 穿过 VFS、*页缓存*、文件系统、块层和驱动，再被中断叫回来。剩下的工程都在少走那扇门：一次多带几件事，或者干脆不进门。 {#sum .sum tag=div}
