## How do we squeeze any length of text into a fixed-size fingerprint? {#step0 h2=s0t}

::: strings
nav0: 0 Fingerprint
:::

Step 0 · The fingerprint {#s0k .step-kicker i18n=text}

This step answers: how does a **hash function** turn input of any length into a fixed-length “fingerprint”? This page uses a teaching 32-bit hash (FNV-1a plus one mixing step; it is **not** a cryptographic hash): the output is always 32 binary digits (0 or 1), whether the input is one character or ten thousand. Type text in the box or press a preset and watch the 32 cells (lit = 1) change. The presets abc and abd differ by a single character, yet the fingerprints look nothing alike. The slider “keep only the last k bits” imitates a shorter fingerprint (hash tables often use h mod 2^k): dimmed bits are discarded and the readout shows the value of the part that is kept. The same input always gives the same output (determinism). {#s0e .explain}

## Change one bit: how much does the fingerprint change? {#step1 h2=s1t}

::: strings
nav1: 1 Avalanche
:::

Step 1 · The avalanche effect {#s1k .step-kicker i18n=text}

This step answers: when the input differs in just 1 binary digit, how much does the output differ? A good hash function shows the **avalanche effect**: flipping any 1 input bit flips about half of the 32 output bits. The picture shows a random 8-byte message (64 input bits): the top row is the original fingerprint, the bottom row the fingerprint after flipping bit p, and orange cells are the bits that changed. Drag “bit to flip”; then press “Run statistics”: for 20 new messages every one of the 64 bits is flipped (1280 flips in all) and the number of changed output bits is accumulated into a histogram that should be centred on 16. The more the bars cluster around 16, the better the diffusion. {#s1e .explain}

::: html step1-1
cv1: Fingerprints before and after the flip, and the histogram of changed bits
s1pL: Bit to flip (0–63)
s1run: Run statistics: 1280 flips
s1new: New message
s1reset: Clear statistics and reset
:::

The avalanche effect is a property of a good hash, not the same as security: the hash on this page has no attack-resistant design and must not be used for passwords or signatures. {#s1term .term i18n=text}

::: strings

:::

## Use the fingerprint as an address: which slot does a key land in? {#step2 h2=s2t}

::: strings
nav2: 2 Hash table

Step 2 · The hash table {#s2k .step-kicker i18n=text}

This step answers: how do we use a hash to store and find things fast? A **hash table** has m slots (buckets) and puts a key into bucket number h(key) mod m. The picture drops keys key-001, key-002, … in one after another: several keys landing in the same bucket is a **collision**, and keys in one bucket are stacked in a column (orange). Drag the number of keys n and the number of buckets m, keeping one fixed, and see how collisions change. The **load factor** α = n / m: the larger α, the more collisions. The readout compares the actual number of occupied buckets with the expected value m·(1 − (1 − 1/m)ⁿ) (the formula assumes a uniformly random hash; this page uses one fixed set of keys, so the two will not match exactly). {#s2e .explain}

## Why do collisions arrive earlier than you expect? {#step3 h2=s3t}

::: strings
nav3: 3 Birthday paradox
:::

Step 3 · The birthday paradox {#s3k .step-kicker i18n=text}

This step answers: if n things are dropped at random into m slots, how big must n be before two almost surely collide? The classic example is birthdays: with m = 365, just n = 23 people give about a 50% chance that two share a birthday, because what is compared is not “each person against 365 days” but n(n−1)/2 pairs of people. **Exact probability**: P(at least one collision) = 1 − (1 − 1/m)(1 − 2/m)…(1 − (n−1)/m). Choose an m, drag n, then press “1 / 100 / 1000 experiments”: each experiment drops n items at random and checks for a collision; the orange line is the fraction of experiments so far that had a collision and the green dashed line is the exact probability, which the orange line approaches as experiments accumulate. The probability is about 50% when n ≈ 1.18·√m. Dragging n or changing m clears the experiments done so far. {#s3e .explain}

## How many bits does a fingerprint need to avoid collisions? {#step4 h2=s4t}

::: strings
nav4: 4 How long
:::

Step 4 · How long a fingerprint {#s4k .step-kicker i18n=text}

This step answers: when fingerprinting a huge number of files, how long must the fingerprint be to almost never collide? Assume the hash output behaves like a uniformly random k-bit number; then n objects have at least one collision with probability about 1 − e^(−n(n−1)/2^(k+1)) (about n(n−1)/2^(k+1) when small). The vertical axis is the logarithm of the collision probability (1e-6 = one in a million) and the horizontal axis the fingerprint length k. Drag n (as a power of 10) and k: with n fixed, every extra bit of k roughly halves the probability; the readout also tells you roughly how many bits push it below one in a million. A 32-bit fingerprint almost surely collides at a million objects, and only around 128 bits can collisions be treated as “never happens”. {#s4e .explain}

s4xL: Number of objects n (power of 10)
s4kL: Fingerprint length k
s4reset: Reset
:::

Assumes hash outputs that are uniformly random and independent; real hashes (especially non-cryptographic ones) can be biased and an attacker may craft collisions deliberately, which this page does not cover. {#s4term .term i18n=text}

## Wrap-up: fixed-size fingerprints cannot avoid collisions {#step5 h2=s5t}

::: strings
nav5: 5 Finale
:::

Step 5 · Finale {#s5k .step-kicker i18n=text}

A hash squeezes any input into a fixed-length fingerprint: a good hash makes the output look random, and looking random means collisions follow the birthday paradox and can only be pushed down by adding bits. {#s5e .explain i18n=text}
