Step 0 · A function calls itself {#s0k .step-kicker i18n=text}

This step answers: how does a recursion actually get its answer? Take the factorial n! = n × (n−1)! (with 1! = 1, called the **base case**: it can be answered without asking further). Each call of fact(k) adds a layer to the **call stack** (the blocks stacked downward in the picture, meaning “still waiting for the next layer’s result”); only after reaching the base case do the layers **return** from the bottom up, multiplying the results back together. Drag “step reached” or press “Auto play”: in the first n steps the blocks pile up, in the last n steps they turn green from the inside out and show their values. Change n: how deep does the stack get? {#s0e .explain}

Call stack = a pile of calls that have started and are still waiting for a result; base case = the smallest case that is answered directly without recursing. A recursion without a base case never stops. {#s0term .term i18n=text}

## How do you move a whole tower? {#step1 h2=s1t}

::: strings
nav1: 1 Towers of Hanoi
:::

Step 1 · Towers of Hanoi {#s1k .step-kicker i18n=text}

This step answers: with the rules that only one disk moves at a time and a larger disk may never sit on a smaller one, how do we move n disks from peg A to peg C? The recursive idea: first move the top n−1 disks to peg B (using C), then move the largest disk to C, and finally move those n−1 disks from B to C (using A). Moving n−1 disks is the same problem again, so knowing how to move n−1 means knowing how to move n. Drag “move number” or press “Auto play”: watch the disks move one step at a time, and the text under the picture says which of the three phases we are in. The number of moves is T(n) = 2·T(n−1) + 1 = 2ⁿ − 1. {#s1e .explain}

::: html step1-1
cv1: Three pegs and the current positions of the disks
s1nL: Number of disks n
s1kL: Move number
s1reset: Reset
:::

T(n) = the number of moves for n disks; each extra disk doubles the count and adds 1. Every move here follows the recursive solution, which is known to use the fewest possible moves (not proved on this page). {#s1term .term i18n=text}

Step 2 · The recursion tree {#s2k .step-kicker i18n=text}

This step answers: why are some recursions lightning fast and others terrifyingly slow? Draw every call as a block with the subproblems it calls on the next level, and you get the **recursion tree**. Three typical cases: Towers of Hanoi (size drops by 1, splits into 2 subproblems, each call does 1 move); binary search (size halves, enters only 1 subproblem, 1 comparison per call); merge sort (size halves, splits into 2 subproblems, each call merges size elements). Pick one and drag the size: see how the number of blocks per level changes (upper picture) and how the work per level changes (horizontal bars below). Total work = the sum over the levels. {#s2e .explain}

::: html step2-1

k_hanoi: Towers of Hanoi
k_binary: Binary search
k_merge: Merge sort

s2reset: Reset
:::

“Work” counts each one’s basic operation: Hanoi one disk move per call; binary search one comparison per level; merge sort size elements merged per call (leaves free). The three units differ, so only the shapes of growth are compared. {#s2term .term i18n=text}

## Split the big problem, then put it back together {#step4 h2=s4t}

::: strings

Step 4 · Divide and conquer {#s4k .step-kicker i18n=text}

This step answers: in what order does the merge-sort recursion tree actually run in code? The idea is **divide and conquer**: split the array into a left and right half, sort each, then **merge** the two sorted halves into one sorted whole (merging only needs to take the smaller of the two front elements each time, with no re-sorting). Drag “step reached” or press “Auto play”: the orange frame is the range being split, the green frame the range just merged, and below is the recursion stack at that moment (each bar = one level of calls, its length = the range size). The comparison count in the readout never exceeds n·log₂n. “New numbers” swaps in 8 new numbers and goes back to step 0. {#s4e .explain}

::: html step4-1
cv4: How merge sort runs, with its recursion stack
s4kL: Step reached
s4new: New numbers (back to step 0)
s4reset: Reset to the initial array
:::

The range [a, b) means positions a to b−1. Merging makes at most one comparison per element placed, so one level of merging costs at most n comparisons over log₂n levels. {#s4term .term i18n=text}

## Wrap-up: the shape of the recursion tree sets the cost {#step5 h2=s5t}

::: strings
nav5: 5 Finale

Step 5 · Finale {#s5k .step-kicker i18n=text}

Recursion = a base case + reducing the problem to smaller copies of itself; once the calls are drawn as a tree, how many calls each level has and how much each does decide the total cost. {#s5e .explain i18n=text}

::: html step5-1
c1t: Base case and call stack
c1b: Recursion goes deeper layer by layer to the base case, then returns from the bottom up (step 0).
c2t: Towers of Hanoi
c2b: T(n) = 2T(n−1) + 1 = 2ⁿ − 1; each extra disk doubles the moves (step 1).
c3t: Tree shape sets cost
c3b: Shrink by 1 and split in 2 → exponential; halve and enter 1 → logarithmic; halve, split in 2 and do n per level → n·log n (steps 2 and 3).
c4t: Divide and conquer
c4b: Split, solve each part, merge; merging is cheaper than sorting from scratch (step 4).
modelT: Model and limits
modelB: The Hanoi move count and the merge-sort comparison count are exact counts from the code actually running on this page; the time conversions for growth rates assume 10⁹ steps per second. Binary search and Towers of Hanoi are both recursions, but their recursion trees have different shapes and their costs different orders of magnitude, so they are not “equivalent”. This page does not discuss stack overflow or tail-call optimisation, and gives no general form of the master theorem.
:::
